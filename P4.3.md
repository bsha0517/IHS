# 2. SECURITY PRINCIPLE

Assume an attacker may:

* access the public login page
* send arbitrary HTTP requests
* modify request parameters
* manipulate form fields
* reuse IDs from another organization
* attempt cross-branch access
* brute-force authentication
* abuse password reset
* forge origins
* replay requests
* send malformed payloads
* probe APIs/routes
* inspect client-side JavaScript
* attempt session theft/reuse
* exploit unsafe redirects
* trigger expensive endpoints repeatedly

Do NOT assume UI restrictions provide security.

All security must remain enforced server-side.

Confirm passwords use a modern password-hashing algorithm already present in the project.

Examples acceptable conceptually:

* Argon2id

Do NOT invent custom password hashing.

If existing implementation is adequate:

---

# 7. PASSWORD POLICY

Review actual password policy.

For staff/admin accounts establish a sensible V1 minimum.

Prefer:

* reasonable minimum length
* allow passphrases
* no arbitrary complexity circus
* no maximum that breaks password managers except a safe technical upper bound

Do not force periodic password changes merely because old security standards once recommended them.

Do not implement country-specific policy.

---

# 8. LOGIN USER ENUMERATION

Login responses should not reveal whether:

* username exists
* email exists
* password alone is wrong
* account is inactive

to unauthenticated attackers.

Use a generic response where appropriate.

Internal logs may retain safe diagnostic classification.

Do not expose internal status unnecessarily.

---

# 9. LOGIN RATE LIMITING

Public login must have brute-force protection.

Inspect whether any rate limiting already exists.

If absent, implement a production-appropriate mechanism.

Requirements:

* rate limit repeated failed authentication
* consider IP AND account identifier
* avoid permanent account lockout
* successful authentication may reset/reduce relevant counters
* return safe error
* do not expose whether account exists

Avoid purely process-memory rate limiting if production may run multiple/serverless instances.

Prefer a storage-backed design compatible with current architecture.

Do NOT add Redis unless truly necessary.

PostgreSQL-backed rate limiting is acceptable for initial V1 if designed carefully.

---

# 10. ACCOUNT LOCKOUT

Do NOT implement indefinite administrative lockout merely after N failed attempts.

Prefer temporary throttling/backoff.

The objective is brute-force resistance without creating an easy denial-of-service attack against known staff accounts.

---

# 12. RESET TOKEN STORAGE

Raw password-reset tokens should ideally NOT be stored in plaintext.

Preferred:

random token
→ send raw token to user
→ store secure hash/digest
→ compare digest on use

If raw tokens are currently stored:

fix if practical without breaking architecture.

Do not log tokens.

---

# 13. RESET TOKEN EXPIRATION

Verify expiration is enforced server-side.

Expired token:

must fail even if UI still has the link.

---

# 14. RESET TOKEN SINGLE USE

After successful password reset:

the token must become unusable.

Test replay.

---

# 15. PASSWORD RESET AND EXISTING SESSIONS

Decide explicitly what happens to existing staff sessions after password reset.

Preferred security behavior:

invalidate other sessions for that user.

If current session architecture makes this impractical, document it as a HIGH security backlog rather than pretending password reset automatically invalidates sessions.

Do not redesign authentication unnecessarily.

# 16. SESSION TRACE

Trace actual Session model and cookie behavior.

Verify:

* cryptographically strong session token
* server-side session state
* expiration
* inactive user rejection
* organization status rejection where appropriate
* cookie HttpOnly
* cookie Secure in production

* session deletion on logout

---

# 17. SESSION FIXATION

On successful authentication:

ensure the user receives a new session.

Do not reuse an unauthenticated/pre-existing session identifier.

---

# 18. LOGOUT

Logout should invalidate the server-side session, not merely remove the browser cookie.

Verify with test:

login
→ capture session
→ logout
→ attempt reuse
→ rejected.

---

# 19. SESSION EXPIRATION

Verify expired server-side sessions cannot authenticate even if a cookie remains.

Do not rely only on browser expiration.

---

# 20. USER DEACTIVATION

If Admin deactivates a User:

existing sessions should no longer grant access.

If this already occurs because every session resolution checks user status:

prove it.

If not:

fix.

This is important.

---

# 21. ROLE / BRANCH CHANGES

Determine behavior when an Admin changes:

* User roles
* User branch access

Existing sessions must not preserve stale authorization indefinitely.

Prefer permission resolution from authoritative DB state or session invalidation/versioning.

Test:

User logged in
→ Admin removes privilege
→ existing session tries privileged action
→ rejected.

Do not rely on logout/login if current security model can reasonably enforce changes immediately.

# 38. CSP

Build a CSP compatible with the actual application.

Prefer:

* restrictive `default-src`
* controlled script/style/font/image/connect sources
* `object-src 'none'`
* `base-uri 'self'`
* `frame-ancestors 'none'` unless embedding is intentionally required
* `form-action 'self'`

Be careful with Next.js runtime requirements.

If nonce-based CSP is disproportionately invasive for this batch, implement the strongest practical static policy and document remaining hardening.

Do NOT deploy a CSP that breaks production.

Test it against a real production build.
