# API.md

Living reference for server architecture, route map, and API conventions. Updated at the end of every phase.

## 1. Conventions

- **Route Handlers** (`/app/api/<domain>/...`) for anything called from client components, webhooks, or future external/mobile integration.
- **Server Actions** for form-bound mutations inside server-rendered pages.
- Both are thin adapters (auth check → validate with Zod → call service) over a shared **domain service layer** (`/lib/domains/<domain>/service.ts`), which is the single source of business logic. No business rule is ever implemented twice for the same operation.
- Standard response shape for Route Handlers: `{ data }` on success, `{ error: { code, message, fieldErrors? } }` on failure, correct HTTP status always set (400 validation, 401 unauthenticated, 403 unauthorized, 404, 409 conflict, 500).
- List endpoints: server-side pagination (`?page=&pageSize=`), sorting (`?sort=field:asc`), filtering via explicit query params per resource — never an unbounded `SELECT *`.
- Mutations are idempotency-safe where duplicate-submit is a realistic risk (invoice creation, payment recording) via a client-generated `Idempotency-Key` header honored by the service layer.

## 3. Middleware

`src/proxy.ts` (Next.js 16 Proxy, the Node-runtime successor to the deprecated `middleware.ts` — see ARCHITECTURE.md §16) resolves the session from the cookie against the database, and default-denies any route not matched to an explicit public allow-list (`/login`, `/api/auth/*`, `/book`, `/portal/login` — the last two added in Phase 12, see ARCHITECTURE.md §13). Phase 12 also gave `/portal/*` its own branch: a separate `PatientPortalSession` cookie check, not the staff session check every other route gets. `/api/reports/export` (Phase 13) needed no new branch — it falls under the default staff-authenticated class like every dashboard page, and additionally re-checks `reports.export` plus the requested category's own permission inside the handler itself (the same "no layer trusts the layer above it" discipline as everywhere else, ARCHITECTURE.md §16).

## 4. Forward Route Map (populated per phase)

- **Phase 12 (prediction, not what actually shipped)**: this entry once predicted `/api/portal/*` and `/api/public/booking/*` Route Handlers. Phase 12 actually built both the Patient Portal and Online Booking entirely via Server Actions (`src/app/portal/actions.ts`, `src/app/book/actions.ts`) — server-rendered pages with form-bound mutations, the same pattern every other domain uses, needed no client-callable REST endpoint after all. Left here, corrected, rather than deleted, since the wrong prediction and why it didn't hold is itself useful context for the next phase's forward-looking notes.
- **Phase 13 (what actually shipped, not a prediction)**: `/api/reports/export` — the codebase's first real Route Handler, and the reason turned out to be a plain file download (correct `Content-Disposition`/`Content-Type` headers, a browser-navigable URL), not an external/mobile integration need the way this section originally anticipated. See §3 and PROJECT_STATUS.md's Phase 13 Architecture Decisions.

## Status

Phase 14 (Hardening — the last phase in spec.md's roadmap) added no new routes or action modules; it's a review-and-fix phase (tests, indexing, error boundaries, documentation corrections — see PROJECT_STATUS.md), not a feature phase. The one API-surface-relevant change: `(dashboard)/error.tsx`, `(dashboard)/not-found.tsx`, `portal/error.tsx`, `book/error.tsx`, a root `not-found.tsx`, and `global-error.tsx` were added — every route this document describes now has a real error/not-found boundary instead of falling through to Next's default, unstyled one. Phases 1 through 12 were all implemented via Server Actions — no dedicated `/api/*` route handlers existed, since nothing built through Phase 12 needed to be called from outside a server-rendered page's own form/dialog (no public/unauthenticated endpoint, no webhook, no third-party client — Phase 12's public booking flow and portal login are both server-rendered pages with their own forms, not API clients). Phase 2 action modules, following the same pattern as Phase 1: `src/app/(dashboard)/patients/actions.ts` (including a `searchPatientsAction` used by the live patient-picker combobox — a Server Action called directly from a client component, not a REST endpoint, which is a legitimate and simpler alternative to a `/api/patients/search` route for this internal-only use case), `src/app/(dashboard)/providers/actions.ts`, `src/app/(dashboard)/services/actions.ts`, `src/app/(dashboard)/appointments/actions.ts`. Phase 3 adds one large `src/app/(dashboard)/encounters/actions.ts` covering every clinical mutation (vitals, notes, amendments, diagnoses, orders, prescriptions, follow-ups, encounter lifecycle) rather than splitting per-sub-resource — the encounter workspace is a single page compositing all of these, so one action module matching that page mirrors the actual call-site shape instead of an arbitrary REST-style split. Phase 4 follows the same page-shaped-module convention: `src/app/(dashboard)/pos/actions.ts` (cashier session lifecycle, ad-hoc charges, invoice generation, payment recording — everything the POS workspace itself calls), `src/app/(dashboard)/invoices/actions.ts` (void, refund request/authorize/reject/complete — invoice-detail-page mutations), `src/app/(dashboard)/packages/actions.ts` (package master, purchase, session consumption). Phase 5 adds `src/app/(dashboard)/inventory/actions.ts` (product master, stock adjustments, transfers), `src/app/(dashboard)/suppliers/actions.ts`, and `src/app/(dashboard)/purchasing/actions.ts` (purchase requests through goods receipt and supplier payment — the whole procurement chain in one module, since `/purchasing` is a single tabbed workspace page); the consumption-template action lives in `src/app/(dashboard)/services/actions.ts` instead of the inventory module, since it edits a Service, not a Product. Phase 6 adds `src/app/(dashboard)/accounting/actions.ts` (chart-of-account CRUD, account-mapping upsert, manual journal entry — everything the tabbed `/accounting` workspace calls, same one-module-per-page convention) and `src/app/(dashboard)/expenses/actions.ts` (a separate module, not folded into the accounting one, since `/expenses` is its own page with its own permission surface — `expense.create` is granted more broadly than `accounting.post`, e.g. to Clinic Manager); no new action module for `/receivables`/`/payables`, which are read-only views composing existing `billing`/`procurement` list functions (`listOutstandingInvoices`, a new addition to `billing/invoices.ts`) plus Phase 5's existing `purchasing/record-payment-dialog.tsx` and its action, reused rather than duplicated. Phase 7 adds one action module per page, same convention: `src/app/(dashboard)/employees/actions.ts`, `attendance/actions.ts` (mixes the `(prevState, formData)` dialog-form shape with bare direct-call actions for the one-click check-in/check-out buttons — `checkInSimpleAction(employeeId, branchId, shiftId)`/`checkOutSimpleAction(attendanceRecordId)` — the same dual-shape precedent Phase 5's `purchasing/actions.ts` established for its approve/reject buttons), `leave/actions.ts`, `payroll/actions.ts` (plus a payroll-run-detail-page-scoped `payroll/[id]/` isn't a separate action module — the run-detail page's mutations live in the same `payroll/actions.ts` as the list page's, since they're one workflow), `commissions/actions.ts`, `assets/actions.ts`. `providers/actions.ts` gained one new action (`linkEmployeeAction`) rather than a new module, since it's a single field on an existing entity's detail page, not a new page. Phase 8 adds `src/app/(dashboard)/laboratory/actions.ts` (lab test/panel catalog CRUD, assign-tests, specimen collection/rejection, numeric/text result entry, verification — everything the Lab Queue and order-detail pages call, one module across both since they're one workflow, the same reasoning already applied to `payroll/actions.ts` spanning the payroll list and run-detail pages in Phase 7). Phase 9 adds `src/app/(dashboard)/pharmacy/actions.ts` (medication catalog CRUD, create/verify/dispense/return dispensing records, plus `setPharmacyEnabledAction` for the Admin Settings module toggle — everything the Pharmacy Queue and prescription-dispensing detail pages call, one module across both, the identical one-module-per-workflow reasoning already applied to Phase 8's `laboratory/actions.ts`); the toggle action itself lives in the pharmacy module rather than a new `admin/settings/actions.ts`, since it's pharmacy-domain business logic (`setSetting` gated on `settings.edit`) invoked from a settings-page UI, not settings-domain logic. Phase 10 adds `src/app/(dashboard)/radiology/actions.ts` (imaging service catalog CRUD, assign-service, scheduling, mark-performed, write-report, verify — everything the Radiology Queue and order-detail pages call, one module across both, the same convention as Phase 8's `laboratory/actions.ts` and Phase 9's `pharmacy/actions.ts`). Phase 11 adds two action modules rather than one, reflecting that its domain is genuinely two workflows sharing one service folder: `src/app/(dashboard)/payors/actions.ts` (Payor/InsurancePlan/Policy catalog CRUD — everything the `/payors` workspace's three tabs call) and `src/app/(dashboard)/claims/actions.ts` (claim create/submit/adjudicate/resubmit, remittance recording, *and* the patient-coverage/prior-authorization mutations surfaced on Patient 360's Insurance tab and the invoice detail page's "Create claim" dialog — grouped here rather than in `patients/actions.ts` because they're claims-domain mutations displayed on someone else's page, the same "action lives with the domain that owns the mutation, not the page that happens to render it" convention already established when `packages/actions.ts` supplied the dialogs Patient 360 uses to sell/consume packages). Four routes outside the `(dashboard)` group: `/prescriptions/[id]/print` (Phase 3), `/invoices/[id]/print` (Phase 4), `/laboratory/orders/[id]/report` (Phase 8), `/radiology/orders/[id]/report` (Phase 10) are standalone server-rendered pages (not Server Actions, not API routes) so they can render without the app's dashboard chrome for printing/PDF handoff — Phase 9 added no new print/report view of its own (spec.md §29 doesn't name a standalone dispensing document the way it does for prescriptions/invoices/lab/radiology reports), and Phase 11 likewise added none (spec.md §39 doesn't name a standalone claim-form print view; the claim detail page inside the dashboard chrome is sufficient for a system that doesn't submit claims via a printed/faxed form). Phase 12 adds five action modules across three surfaces rather than one, reflecting that its domain spans staff, portal, and public contexts: `src/app/(dashboard)/communications/actions.ts` (template CRUD, manual sends from the Communications hub), an extension to `src/app/(dashboard)/patients/actions.ts` (`enablePortalAccessAction`/`resetPortalPasswordAction`/`deactivatePortalAccessAction`, surfaced from Patient 360's Portal Access card — the same "action lives with the domain, page renders it" convention as Phase 11's claims actions on the invoice/Patient-360 pages), an extension to `src/app/(dashboard)/admin/settings/actions.ts` (`setPortalClinicalReleaseAction`, alongside Phase 9's pharmacy toggle), `src/app/portal/login/actions.ts` and `src/app/portal/actions.ts` (the portal's own login/logout/profile-update actions, scoped to `PortalSessionContext` not `SessionContext` — a genuinely different action shape, since these check no RBAC permission at all), and `src/app/book/actions.ts` (seven actions wrapping the public booking wizard's steps, callable with no session of any kind). Phase 13 adds **zero** new action modules — the first phase to add none — because Analytics has no mutations: every dashboard tile and report row is a read, and its one genuinely new capability (CSV export) needed a Route Handler, not a Server Action, for the reason below.

The `/api/*` Route Handler layer described above was speculative through Phase 12 — correctly so in hindsight: Phase 12's public booking flow and portal login both turned out to need only server-rendered pages with their own forms (see the Forward Route Map's corrected Phase 12 entry above), not a client-callable REST endpoint. Phase 13's CSV export is the actual first real need: `src/app/api/reports/export/route.ts` returns a file with `Content-Disposition: attachment` and a real `Content-Type`, which only a Route Handler (not a Server Action, which has no equivalent response-header control) can produce correctly.
