**Phase 2 — Patient & Practice**:
- **Patient**: full registration form (spec.md §9 field set), MRN via number sequence, duplicate detection (phone/email/national ID/name+DOB) that warns rather than blocks, with the override reason captured to the audit trail. Medical profile (allergies/conditions/medication history) with a per-record `isAlert` flag that surfaces as a visible banner on the Patient 360 header.
- **Patient 360**: header (MRN, age — always calculated from DOB, never stored — alerts), and 18 tabs matching spec.md §10 exactly. Overview, Timeline, Medical Profile, and Appointments are fully live; the remaining 14 (Episodes, Encounters, Vitals, Diagnoses, Prescriptions, Orders, Lab Results, Imaging, Procedures, Packages, Invoices, Payments, Documents, Communications) render a labeled "scheduled for Phase N" placeholder rather than being silently absent, since those domains don't exist yet.
- **Timeline**: built entirely from existing structured records (registration timestamp + appointment status history) per spec.md §11 — no separately-maintained timeline table.
- **Provider**: full master (type, specialty, license, fee, default duration), branch/department assignment, and an optional 1:1 link to a `User` login (added beyond the original Phase 2 schema sketch — needed so a doctor can see "their" queue, per spec.md §20).
- **Provider Scheduling**: weekly working-hours entries (multiple rows per day model a break between them) and leave blocks. Leave blocks are enforced as a hard booking-time check (spec.md §16 — "approved leave automatically blocks availability"); working hours themselves are informational for Phase 2 rather than a hard constraint (the hard constraints are the two named in §16: provider and room double-booking).
- **Service**: master with code/category/duration/price/required room type/eligible providers.
- **Appointment**: booking with a live patient-search picker, status workflow (scheduled → confirmed → arrived → checked_in → waiting → in_consultation → completed, plus cancelled/rescheduled/no_show) with full status history, and **database-level double-booking prevention** — a Postgres `EXCLUDE USING gist` constraint on `(provider_id, tstzrange(start_time, end_time))` and the equivalent for `room_id`, not just an application-layer check (spec.md §16's "Prevent" list). Verified live: a conflicting booking attempt is rejected with a readable message, not a raw DB error. Reschedule creates a new appointment linked back to the original (`rescheduledFromId`) rather than mutating the original's time in place, preserving both as real history.
- **Reception & Queue**: a reception workspace (today's branch schedule, waiting list, quick booking, quick registration link) and a queue view (a provider's own queue when their login is linked to a `Provider` record, plus a branch-wide queue for staff with check-in rights). Queue tokens (`Q-001`, ...) are generated through the same concurrency-safe number-sequence mechanism as MRNs/appointment numbers, extended with a **daily-reset** mode (added this phase) — still a single atomic `UPDATE ... RETURNING`, not a second unguarded step.
- Domain events registered and dispatched (transactional outbox, dispatched immediately after the writing transaction commits rather than via a timer — see ARCHITECTURE.md §15): `PatientRegistered`, `AppointmentBooked`, `AppointmentCheckedIn`. The last one has a real handler — it creates an internal `Notification` for the provider's linked user, matching spec.md §64's "Patient waiting" example — the other two are registered no-op placeholders (honestly deferred to Phase 12, not faked).

**Phase 3 — Core EMR**:
- **Episode**: optional grouping above encounters (`title`, `status`), created from a patient's profile or inline when starting an encounter. `Episode (1)—(N) Encounter`.
- **Encounter**: the clinical workspace's spine — `active → completed → finalized`, one-way. Created either from a checked-in appointment (reuses `callPatient()` from the appointments domain when the appointment is still `waiting`, so the two domains stay in sync without a second manual action) or as a standalone walk-in encounter. `completeEncounter()` closes the linked appointment/queue entry too, if any. `finalizeEncounter()` is the one-way lock (spec.md §25/§92): bulk-flips every `draft` note on the encounter to `finalized` and the encounter itself to `finalized`, inside one transaction.
- **Vitals**: height/weight/BP/pulse/temp/SpO2/resp. rate/glucose, with BMI computed server-side (`computeBmi()`) — never trusted from the client, never stored as a raw client-submitted value.
- **Consultation Note**: structured fields (chief complaint, HPI, review of systems, exam findings, assessment, treatment plan) plus a free-text `content` fallback. Freely editable in place while in `draft` status; once `finalized`, `saveNote()` throws and the UI switches to a read-only view with an "Amend" action. **Amendment creates a new row** (`amendsId` → original, `isCurrent` flipped) — the original finalized note is never overwritten, full version chain preserved and browsable via `getNoteHistory()`.
- **Diagnoses**: ICD-coded (`diagnosis_code` seed table, ~30 codes across 12 categories, admin-importable per the BLUEPRINT.md §43 decision), primary/secondary flag, live search-as-you-type combobox. Status (`active|resolved|ruled_out`) independently trackable per diagnosis without touching the note.
- **CPOE Orders**: one shared `ClinicalOrder` parent (number, priority, status, reason/instructions) + concrete per-type detail tables — `LabOrderDetail`, `ImagingOrderDetail`, `ProcedureOrderDetail`, `ReferralOrderDetail` (referral additionally scoped `internal|external` with its own `referred_to_provider_id`/`referred_to_external`). Deliberately not a generic EAV/JSON-blob design. **Medication orders were scoped out of CPOE** — prescriptions (below) are the single path for medications in Phase 3, since a parallel `medication_order_detail` would just duplicate `Prescription`/`PrescriptionItem` with no behavioral difference yet; revisit only if Phase 9 (Pharmacy) needs order-vs-prescription to diverge.
- **Prescriptions**: multi-item (`PrescriptionItem`: medication, generic name, strength, dose, frequency, route, duration, quantity, instructions), `active|cancelled` status, sequence-numbered (`RX-000001`). A standalone printable view (`/prescriptions/[id]/print`, outside the `(dashboard)` route group so it renders without the app chrome) for physical/PDF handoff to the patient.
- **Follow-up recommendations**: modeled explicitly (`follow_up_recommendation`: `recommendedDate`, `reason`, `status(open|scheduled|dismissed)`) per the Phase 0 correction — never inferred from a future appointment's free-text note.
- **Patient 360 wiring**: Episodes/Encounters/Vitals/Diagnoses/Prescriptions/Orders are now 6 live tabs (`LIVE_CLINICAL_TABS`), leaving 8 genuinely-future tabs (`FUTURE_TABS`) each labeled with the phase that will build it.
- Domain event `EncounterFinalized` — registered, no-op (billing charge-capture handler lands in Phase 4).

**Phase 4 — Revenue**:
- **Billing engine** (spec.md §33): a single centralized entry point — `Charge` is the only thing that ever becomes an `InvoiceLine`, and nothing (including the POS UI) writes billing data any other way. `generateSystemCharge()` (internal, no user-facing permission check — used only by trusted system triggers) vs `createAdHocCharge()` (the POS-facing path, gated on `charge.create`) share one underlying insert so `amount` is always server-computed from `quantity × unitPrice`, never accepted as a total from the client.
- **`EncounterCompleted` domain event wired to a real handler** — generates the "Consultation" charge automatically, using the linked appointment's `Service.price` if the visit was booked against a priced service, else falling back to the provider's `consultationFee`. This is the literal `EncounterCompleted` event spec.md §73 names as an example (not the `EncounterFinalized` event this codebase invented last phase) and matches the Core End-to-End Test's explicit ordering (spec.md §85: "Consultation Completed → Charges Generated", before finalization) — billing triggers when the visit is done, not when the doctor later locks their notes. Idempotency-guarded (skips if a consultation charge already exists for the encounter) against outbox at-least-once redelivery.
- **POS** (`/pos`): patient search → pending charges (auto-generated + ad-hoc) → select charges + optional document discount → generate invoice. Ad-hoc charges support `procedure`/`product`/`package`/`other` sources, optionally prefilled from the Service catalog. Requires an open cashier register (spec.md §37's "Open Register → Transactions" ordering) before any payment can be recorded.
- **Invoice**: `subtotal`/`taxAmount`/`totalAmount` computed once at generation time from the selected Charges — tax looked up per line from `TaxRule` (service-specific, else org default, else 0 — never a hardcoded rate), rounded per line then summed (ARCHITECTURE.md §6's locked convention). `paidAmount` is maintained exclusively by the payments/refunds services, never set directly. Void only permitted with zero payments applied (never deletes — reverts consumed Charges back to `pending` so they can be re-invoiced).
- **Payments**: split-tender support (spec.md §35) — one POS submission can record N tenders (cash/card/bank/online/insurance/credit/other) against one invoice in a single transaction, each becoming its own `Payment` + `PaymentAllocation` row (never blended into one row, so each tender stays individually reversible). `Payment:Invoice` modeled many-to-many via `PaymentAllocation` per the Phase 0 architecture decision, even though Phase 4's UI only exercises the 1-payment-1-invoice path.
- **Refunds** (spec.md §36): Request → Authorize → Complete, each a distinct step with `refund.request` vs `refund.authorize` as separate permissions (segregation of duties, same pattern as Phase 3's `lab_result.enter`/`verify`). Completion decrements `Invoice.paidAmount` and recalculates status — the original `Payment` row is never touched or deleted, matching spec.md §92's "never delete financial transactions to reverse them."
- **Cashier sessions** (spec.md §37): Open Register → Transactions → Cash Movements → Close Register. `expectedCash` is always derived at close time (`openingCash` + completed cash `Payment`s during the session + `in` movements − `out` movements − completed cash `Refund`s), never a directly-mutable running balance — verified live with a deliberate 5.00 short count.
- **Packages** (spec.md §32): `Package` master (organization-wide catalog, no `branchId`, matching `Service`'s precedent) bundling N sessions of one or more Services. Sold through the identical Charge → Invoice → Payment path as everything else (source type `package`). `PatientPackage` goes `active` immediately at purchase regardless of payment status — the service is usable before payment settles, which is the entire point of separating Charge from Invoice/Payment (spec.md §33). "Every session consumption requires history" (spec.md §32) is `PatientPackageSession`, an append-only log — remaining sessions are always `COUNT()`-derived per service, never a mutable counter, matching the discipline already established for stock ledgers (ARCHITECTURE.md §7).
- **Patient 360 wiring**: Packages/Invoices/Payments are now 3 more live tabs (9 of the original 18 spec.md §10 tabs now live). The redundant "Procedures" future-placeholder was removed — procedure orders already surface under the existing Orders tab, so a second "coming soon" tab for the same content would have been actively misleading.
- Printable Invoice (`/invoices/[id]/print`, outside the dashboard route group, same pattern as the Phase 3 prescription print view) per spec.md §82.
- Domain events `InvoiceIssued`, `PaymentReceived`, `RefundCompleted` — registered, no-op (accounting posting is the real Phase 6 subscriber; honestly deferred, not faked).

**Phase 5 — Inventory & Procurement**:
- **Product master** (spec.md §41): SKU, barcode, category, brand, unit, purchase cost, selling price, reorder level, minimum/maximum stock. Organization-wide catalog, no `branchId` — same precedent as Service/Package; stock itself is tracked per branch.
- **Stock ledger** (spec.md §43): `StockLedgerEntry` is the single source of truth for on-hand quantity — nothing stores a directly-mutable count anywhere, including on `ProductBatch` (its `receivedQuantity` is a historical fact, not a running balance). Balance is always `SUM(quantity)` with a signed column (positive = in, negative = out) rather than separate quantity-in/quantity-out columns — same information, simpler aggregation. Transaction types cover the full spec.md list: purchase, sale, dispensing, treatment_consumption, adjustment, transfer_in/out, damage, expiry, return.
- **Batch & expiry** (spec.md §42): batches carry manufacturing/expiry dates, supplier, and purchase cost. FEFO (first-expired-first-out) consumption implemented as a real allocation algorithm — walks available batches ordered by expiry date ascending (nulls last), deducting across as many batches as needed to satisfy a quantity, not just picking the single oldest batch. Low-stock, out-of-stock, near-expiry (90-day window), and expired alerts are computed live from the ledger and batch table, never stored flags.
- **Automatic clinical consumption** (spec.md §44): `ServiceProductConsumption` templates ("Wound Dressing consumes: Gauze × 2...") are editable from the Services page. Hooked into the billing engine's `insertCharge()` — the one existing chokepoint every Charge already passes through — rather than into CPOE, since Charge is what captures "this service was delivered" regardless of whether the charge was system-generated or POS-entered ad-hoc. Consumption happens in the same transaction as the Charge; insufficient stock throws and rolls back the whole charge (verified live: billing 60× a service needing 120 units against 98 on hand was cleanly rejected with "need 120, have 98", and no orphaned Charge or partial ledger entry was left behind).
- **Suppliers** (spec.md §45): company, contact, phone, email, address, tax number, payment terms, bank details.
- **Procurement workflow** (spec.md §46): Purchase Request → Approval → Purchase Order → Goods Receipt → Supplier Invoice → Payment, verified live end-to-end. Approval is a distinct permission from request creation (segregation of duties, same pattern as Phase 4's `refund.request`/`refund.authorize`). A Purchase Order can be built from an approved Purchase Request (auto-filling branch/product/quantity/cost from the source request) or standalone. **Partial receiving supported by design**: `PurchaseOrderLine.receivedQuantity` is never stored, always derived by summing `GoodsReceiptLine` rows against it, so multiple receipts against one PO can never drift from the derived total; PO status (`partially_received`/`received`) is recalculated the same way after every receipt.
- **Goods receipt creates real inventory movements**: completing a receipt creates a new `ProductBatch` per line (batch numbers are supplier-assigned, never generated) and a `purchase` stock ledger entry, in the same transaction as the receipt itself.
- **Supplier invoice creates the accounts-payable obligation**: recorded as a `SupplierInvoice`/`SupplierPayment` pair; the actual AP ledger/journal posting is Phase 6's central accounting engine — the same deferred-accounting pattern already established on the revenue side in Phase 4.
- **Stock transfers** (spec.md §41's "Transfers"): request → complete workflow; completing a transfer writes the matching `transfer_out`/`transfer_in` ledger pair referencing the transfer row, with a source-branch balance check before either entry is written.
- `TaxRule` extended with an optional `productId` (alongside Phase 4's `serviceId`) — Product Master names "Tax" as a field (spec.md §41), and the tax-rule table was already designed in Phase 4 to eventually cover both.

**Phase 6 — Finance**:
- **Chart of Accounts & Account Mappings** (spec.md §55): `ChartOfAccount` (code/name/type/optional parent, self-referencing hierarchy) seeded with a default 10-account org chart (Cash, Bank, AR, Inventory, AP, Tax Payable, Unearned Revenue, Owner's Equity, Service Revenue, Operating Expenses) at seed time. `AccountMapping` resolves a fixed 14-entry `PostingIntent` taxonomy (`cash|card|bank|online|insurance|credit|other|accounts_receivable|revenue|tax_payable|unearned_revenue|inventory_asset|accounts_payable|expense_default`) to a real account — branch-specific mapping wins, falling back to an org-wide default (`branchId: null`), throwing a clear configuration error if neither exists. No account is ever hardcoded by id/name anywhere outside `resolveAccountId()`.
- **Central Accounting Posting Service** (`src/lib/domains/accounting/posting-service.ts`, spec.md §55 — "operational modules should NOT independently invent journal logic"): the single writer of `Journal`/`JournalLine`. `postJournal()` generates the sequence number, creates the journal + lines, and does a fast application-level balance check before ever hitting the DB trigger. Eight named posting functions cover every accounting-relevant event across Phases 4–6: `postInvoiceIssued` (Dr AR, Cr Revenue and/or Cr Unearned Revenue proportionally split for package-sourced lines, Cr Tax Payable), `postPaymentReceived` (one Dr line per tender's resolved account, Cr AR — generalizes cleanly to split payments), `postRefundCompleted` (Dr Revenue, Cr the refunded tender's account), `postGoodsReceiptCompleted` (Dr Inventory, Cr AP), `postSupplierPaymentRecorded` (Dr AP, Cr the paying tender's account), `postPackageSessionConsumed` (Dr Unearned Revenue, Cr Revenue, pro-rata), `postExpense` (Dr the chosen expense account, Cr the paid-via tender's account), and `postManualJournal` (the one path accepting arbitrary caller-supplied lines directly, for accountant corrections).
- **Sync vs. async posting, a deliberate split**: `InvoiceIssued`, `PaymentReceived`, `RefundCompleted` (Phase 4 events, now with real handlers) plus three new events fired this phase — `GoodsReceiptCompleted` (from `procurement/goods-receipts.ts`), `SupplierPaymentRecorded` (from `procurement/supplier-invoices.ts`), `PackageSessionConsumed` (from `packages/service.ts`) — all post via the existing outbox pattern (async, after the triggering transaction commits): a missing account-mapping configuration should never block a clinical/revenue/inventory action, so a posting failure just leaves the outbox event `failed` for retry, not roll back the state change that already happened. Expense creation and Manual Journal entry post **synchronously**, in the same transaction as the row itself — these are direct accountant actions expecting immediate confirmation the entry succeeded, not a background side effect of something else.
- **Journal balance enforced at the database, not just in application code**: a `CHECK` constraint (`debit`/`credit` on a line are never both zero or both nonzero) plus a `DEFERRABLE CONSTRAINT TRIGGER ... INITIALLY DEFERRED` (`journal_line_balance_check`) that sums every line on a journal and raises if `Σdebit ≠ Σcredit`, checked at end-of-transaction so a multi-`INSERT` journal write (create journal → create N lines, one at a time) never trips the trigger mid-construction. Verified live: a hand-crafted unbalanced journal (Dr 100 / Cr 50) was cleanly rejected at commit with `"Journal ... is unbalanced: total debit 100.00 does not equal total credit 50.00"`, and a real balanced manual journal posted through the actual UI committed successfully.
- **Financial reports** (`src/lib/domains/accounting/reports.ts`) — Trial Balance, Income Statement (P&L), Balance Sheet, and a simplified direct-method Cash Flow (every journal line touching a Cash/Bank-mapped account, grouped into inflows/outflows), all computed live from `journal_line` at read time via one raw `GROUP BY account_id` query per report — never a stored/cached total (spec.md §92's "never trust frontend totals" extended to "never trust a stale server-side aggregate either"). Balance Sheet's Equity section includes current-period net income as an unlabeled-account "Retained Earnings (current period)" line rather than requiring an explicit period-close step, since nothing in this build yet closes the books.
- **Accounting UI** (`/accounting`): tabbed workspace — Chart of Accounts, Account Mappings, Journals (with a per-journal line-detail view), Trial Balance, Income Statement, Balance Sheet, Cash Flow — plus a Manual Journal entry dialog with live client-side balance feedback (debit/credit running totals, submit disabled until they match) backing the DB trigger, not replacing it. `/expenses` (record + list, scoped to expense-type accounts only). `/receivables` (every invoice still owed money, oldest first — new `listOutstandingInvoices()`). `/payables` (outstanding supplier invoices, reusing Phase 5's existing `RecordPaymentDialog` rather than building a second one).
- **Revenue-cycle integration verified end-to-end via direct service-layer calls** (browser automation couldn't reliably drive Radix `Select`/`Tabs` in this session's environment — see Known Issues): ad-hoc charge → invoice → split payment (cash 600 + card 400) → partial refund (150) → all three postings correct and individually balanced, overall trial balance still balanced (`totalDebit === totalCredit === 1350`) after all three. Goods receipt (10 units × 5.00) → `Dr Inventory 50 / Cr AP 50`. Supplier payment (50.00 bank) → `Dr AP 50 / Cr Bank 50`. Package purchase (900.00, 10 sessions) + one session consumed → pro-rata `Dr Unearned Revenue 90 / Cr Revenue 90` (900/10). Expense (75.00 bank) → `Dr Operating Expenses 75 / Cr Bank 75`. Final combined trial balance across every posting: balanced.

**Phase 7 — HR & Assets**:
- **Employee master** (spec.md §49): `Employee` (number via the `EMP` sequence reserved since Phase 1 but never used until now, personal details, department, designation, manager self-relation, joining date, employment type, basic salary, bank details, status) plus `EmployeeDocument` (ID/passport/visa/contract/license/certification, with expiry tracking) — metadata only, no file storage, the same deliberate scope call already made for `patient_document` in Phase 2 (spec.md §49's actual requirement is "track expiry," not a document-management system). `Provider.employeeId` (nullable, unique 1:1, present in the schema since Phase 2 but never wired to anything) is now a real FK, surfaced both directions: the Employee detail page shows "Provider profile: Linked/Not linked," and a new small `LinkEmployeeDialog` on the Provider detail page — added this phase after noticing the DB relation existed with no UI path to actually set it — lets staff attach an Employee to a Provider (spec.md §14 names "Employee" as a Provider field).
- **Attendance** (spec.md §50): `Shift` (named work pattern, branch-local `HH:MM` times, same convention as `ProviderSchedule`) + `AttendanceRecord` (one row per employee per date). `workingMinutes`/`lateMinutes`/`earlyDepartureMinutes`/`overtimeMinutes` are always computed server-side at check-out against the assigned shift's times — never accepted as a client-submitted value (same discipline as `VitalSign.bmi` since Phase 3). "Maintain adjustment audit trail" (spec.md §50) is satisfied by the standing `audit_log` mechanism, not a bespoke second log table.
- **Leave** (spec.md §51): Employee → Request → Manager Approval workflow (`leave.request` vs `leave.approve` as distinct permissions, segregation of duties, the same pattern as every prior phase's request/approve pair). `LeaveBalance` stores only the entitlement (`allocatedDays`); used/remaining are always derived live by summing approved `LeaveRequest.days`, never a stored running balance. **"Doctor leave must affect scheduling" implemented for real**: approving a leave request for an employee linked to a Provider creates a matching `ProviderLeaveBlock` — the exact mechanism Phase 2's booking-conflict check already reads — via a newly-real `EmployeeLeaveApproved` handler (the event was reserved in ARCHITECTURE.md's table since Phase 2 but never wired until now).
- **Provider Commissions** (spec.md §53): `CommissionRule` supports all five named types/scopes (fixed, percentage, tiered; provider-specific, service-specific, product-specific, or org-wide default) resolved most-specific-wins, and all three named bases (gross invoice, net invoice, collected revenue). **A real accounting distinction drove a two-trigger design, not a shortcut**: gross/net-invoice-basis rules accrue once, at `InvoiceIssued` time (the amount is fixed and known then, and accruing per-payment would double-count across a split/partial payment); collected-revenue-basis rules accrue per payment, proportional to what that specific payment actually collected against each charge, keyed to the real `Payment` row id for idempotency. Verified live: a 10% collected-revenue rule against a 1000.00 charge, paid in full in one tender, accrued exactly 100.00. **Found and fixed a real gap while building this**: `createAdHocCharge`'s schema had no `providerId` field at all — every ad-hoc POS charge (procedures, products, walk-in add-ons) was unattributable to a provider, silently defeating commission tracking for anything except system-generated consultation charges. Added `providerId` to `adHocChargeSchema`, threaded it through to `insertCharge` (which already supported it), and added a Provider selector to the POS "Add charge" dialog.
- **Payroll** (spec.md §52): Draft → Review → Approved → Paid workflow. Creating a run pulls each active employee's `basicSalary` plus, for employees linked to a Provider, their `pending` `CommissionAccrual` total for the period — marking those accruals `included_in_payroll` immediately so a second run can never double-count them. `netSalary` (`basicSalary + allowances + overtime + commission + bonus − advances − unpaidLeaveDeduction − otherDeductions`) is stored per line, the same "fixed historical fact once finalized" precedent as `Invoice.totalAmount`. No separate `payslip` table — the payslip is a view over `PayrollRunLine` + `Employee`, matching how Invoice/Payment are already their own printable documents rather than a redundant money-shaped table. Approving a run posts `Dr Salary Expense / Cr Payroll Payable` (spec.md §55's own named example); marking a run paid posts `Dr Payroll Payable / Cr [the run's paidVia tender account]` — both via two new `PostingIntent`s (`salary_expense`, `payroll_payable`) and two new posting-service functions, the same central-posting-service discipline as every Phase 6 posting. Verified live: basic 5000 + commission 100 = net 5100, Approved posted `Dr 6000 Salary Expense 5100 / Cr 2300 Payroll Payable 5100`, Paid posted `Dr 2300 Payroll Payable 5100 / Cr 1010 Bank 5100` — both balanced, and the included commission accrual flipped to `paid`.
- **Assets, Maintenance & Calibration** (spec.md §47/§48): `Asset` (number via the `AST` sequence, all seven named statuses, optional links to department/room/assigned employee/supplier) + `MaintenanceRecord` (preventive/corrective) + `CalibrationRecord` (pass/fail/conditional, medical-equipment-focused per spec but not schema-restricted to a category allow-list — same free-text-category reasoning as `Episode.episodeType`). Warranty-expiring and calibration-due alerts computed live from real dates (30-day horizon), never stored flags — same discipline as Phase 5's low-stock/near-expiry alerts. **Deliberately no accounting posting on asset purchase** — spec.md §47 doesn't name one, and an asset's actual acquisition cost already flows through the existing Expense or SupplierInvoice/Payment paths if bought that way; a second, redundant posting path wasn't built ahead of a real need for it.

**Phase 8 — LIS**:
- **Lab Test Master & Panels** (spec.md §28): `LabTest` (organization-wide catalog, code/category/specimen type/numeric-or-text result type/reference range/unit/price/turnaround) and `LabPanel` (a bundle priced as one line — e.g. "CBC" — that expands into one independently-resulted `LabOrderTest` per member, since a panel produces several distinct results with different reference ranges, not one combined value). Seeded with a small common-outpatient subset (Glucose, Creatinine, TSH, Urine R/M, and a 5-member CBC panel) — same "small real subset, not the full code universe, admin-extendable" precedent as Phase 3's `DiagnosisCode` seed.
- **A deliberate two-stage order model, not a rework of Phase 3's CPOE**: the doctor's existing free-text CPOE lab order (`ClinicalOrder` + `LabOrderDetail`, built in Phase 3, left completely untouched this phase) continues to capture clinical *intent* ("CBC, lytes"); lab staff then translate that intent into structured, catalog-priced, billable `LabOrderTest` lines when accessioning the specimen — the same separation of "what the doctor wants" from "what actually gets coded and billed" a real lab uses. This avoided reopening and re-testing Phase 3's already-shipped CPOE dialog, consistent with the discipline already applied when Phase 5 hooked automatic consumption into the billing engine rather than into CPOE.
- **Specimens and structured results, both real tables, not text fields** (spec.md §28's explicit "do not build a simplistic text-only result system"): `Specimen` tracks the physical sample (number via the `LAB` sequence reserved since Phase 1 but unused until now, type, collection metadata, pending/collected/received/rejected lifecycle) independently from `LabOrderTest`, since one specimen commonly services several tests. `LabOrderTest` snapshots `unit`/reference range from the catalog at **result-entry time** (the actual clinical-interpretation moment), not at order time, so a later catalog edit never silently rewrites an already-entered result's context — the same snapshot-don't-reference-mutable-master-data discipline as Phase 4's `InvoiceLine`. `abnormalFlag` is always computed server-side from the entered value against the snapshotted range, never accepted from the caller — the same discipline as `VitalSign.bmi`/`AttendanceRecord.lateMinutes`.
- **Billing wired at the test-assignment moment**: assigning catalog tests/panels to an order generates one `Charge` per test (or one per panel, covering all its members) via the same `generateSystemCharge()` every other automatic charge already goes through — the first time `ChargeSourceType.lab` (defined back in Phase 4, unused since) actually gets used. Verified live: assigning Glucose + CBC + Urine R/M generated exactly 3 charges (40.00, 100.00, 35.00) against one CPOE order.
- **Result Entry → Verification → Final Result** (spec.md §28): `lab_result.enter` vs `lab_result.verify` as distinct permissions — segregation of duties, the identical pattern every prior phase's enter/verify or request/approve pair has followed since Phase 3. Verifying the last outstanding test on an order rolls `ClinicalOrder.status` to `completed` and fires `LabResultFinalized` — reserved in ARCHITECTURE.md's event table since Phase 2 but never wired until now, mirroring `AppointmentCheckedIn`'s "Patient waiting" notification exactly (notify the ordering provider, no-op if they have no login).
- **Result Reporting**: a standalone printable report (`/laboratory/orders/[id]/report`, outside the dashboard route group, same precedent as the Prescription/Invoice print views), showing only verified lines, with abnormal results visually distinguished.

Not a bug; there's no real denominator to compute a percentage against without inventing room operating hours the schema (and spec) never asked for.
- **AR/AP in the Financial and Revenue Cycle reports are current outstanding balances, not point-in-time historical figures** — `Invoice.paidAmount`/`SupplierInvoice.paidAmount` are current-state fields with no snapshot history, so "AR as of a past date" isn't a real number this schema can produce without reconstructing it from `Payment`/`SupplierPayment` history (not attempted this phase). - **Inventory valuation uses each product's current `purchaseCost`, not a FEFO batch-weighted average** — simpler than reconstructing historical batch cost, the same "documented simplification, not a faked number" standard as Phase 6's simplified direct-method cash flow.
- **"Consumption"/"Fast-Moving"/"Slow-Moving" are defined as `dispensing`+`treatment_consumption`+`sale` stock-ledger movements** — a reasonable, real definition, but a different one than "every outbound movement" (which would also count transfers/damage/expiry/adjustment-out); revisit if a real deployment's definition of "consumption" needs to include those too.
- **No charting library added — `/analytics`'s trend charts are plain CSS bars**, not a Recharts/Chart.js integration. A deliberate "no unnecessary complexity" call for six simple monthly trend bars, the same discipline already applied to not building a background job scheduler (ARCHITECTURE.md §15) — revisit if a real deployment needs richer visualizations (multi-series, zoom, tooltips) a CSS bar can't provide.

A reasonable, real, but incomplete first wiring — extend it if a real compliance review names a specific gap as load-bearing.

Revisit with real `EXPLAIN ANALYZE` output from production query logs if any of these turn out to matter in practice — this pass was a reasoned review, not a guarantee no other index will ever help.

## Architecture Decisions

- **Every `DateTime` field now maps to Postgres `TIMESTAMPTZ`, not the Prisma-on-Postgres default of `TIMESTAMP` (no timezone).** Discovered while adding the double-booking exclusion constraint (which needs `tstzrange`, not `tsrange`) — Prisma's `DateTime` type silently produces a naive `timestamp` column unless `@db.Timestamptz` is specified per field, which contradicts DATABASE.md's own stated convention and BLUEPRINT.md's named timezone-correctness risk. Fixed retroactively across all 53 existing timestamp columns (Phase 1 and Phase 2 alike) via an `ALTER COLUMN ... SET DATA TYPE TIMESTAMPTZ` migration, safe because the underlying Postgres session timezone is UTC (verified via `SHOW timezone` before applying) and there was negligible real data at the time. **Any future `DateTime` field added to the schema must include `@db.Timestamptz(3)` explicitly** — this is now the binding convention, not just an aspiration. Phase 3's new tables followed this correctly from the start (no repeat of the bug).
- **Provider ↔ User link added** (`Provider.userId`, optional, unique) — not in the original Phase 2 schema sketch, but required once the Doctor Queue view (spec.md §20) was actually built: a doctor needs to log in as a `User` and see the `Provider` record's queue, and nothing previously connected those two identities.
- **`prisma migrate dev`'s shadow-database drift detection doesn't work cleanly against a Supabase-hosted database** (it flags Supabase's own pre-installed extensions — `pgcrypto`, `pg_stat_statements`, etc. — as drift). Standardized on generating migrations via `prisma migrate diff --from-config-datasource --to-schema ... --script` and applying them with `prisma migrate deploy`, which doesn't do shadow-DB comparison. Documented here so this doesn't get "fixed" back to `migrate dev` by habit in a later phase and reintroduce the friction. Held for Phase 3 too.
- **Generic `serializeDecimals()` utility added** (`src/lib/utils/serialize.ts`) after the Prisma-`Decimal`-crossing-the-RSC-boundary bug (see Phase 2's Known Issues) recurred a second time with Phase 3's new `Decimal` fields (`VitalSign.heightCm/weightKg/bmi/...`). Rather than hand-picking Decimal-free field subsets at every call site a third time — the exact discipline that already slipped twice — this recursively converts every `Decimal` in a prop tree to `Number` once, applied at the single point data crosses into `encounters/[id]/page.tsx`'s client subtree. Any new Prisma `Decimal` field reaching a Client Component should go through this, not a new one-off mapping.
- **`organizationId` scoping caught proactively on `VitalSign`/`Diagnosis`/`FollowUpRecommendation`** before any query actually leaked across tenants — noticed while writing `listPatientVitals()` that these three Phase 3 models were missing the `organization_id` column every other business table in the schema carries. Fixed via the `clinical_org_scoping` migration before those tables held any real data.
- **CPOE excludes medication orders** — a `ClinicalOrder` with a `medication_order_detail` type would just duplicate `Prescription`/`PrescriptionItem` with no behavioral difference in Phase 3 (no separate lab-style fulfillment workflow for medications yet). Prescriptions are the single path for medications; revisit only if Phase 9 (Pharmacy) needs order-vs-prescription lifecycles to diverge.
- **Billing hooks off `EncounterCompleted`, not `EncounterFinalized`** — spec.md §73 only ever names `EncounterCompleted` as its illustrative domain event, and the Core End-to-End Test (§85) explicitly orders "Consultation Completed → Charges Generated" before any mention of finalization. Phase 3 invented `EncounterFinalized` as its own event without checking this; Phase 4 added the correct `EncounterCompleted` event as the real billing trigger rather than silently reassigning the meaning of the event Phase 3 already shipped. Both events now exist and fire at their respective transitions — `EncounterFinalized` remains a legitimate no-op hook for anything that only cares about the legal-lock moment (e.g. a future compliance subscriber), not removed for lack of a current use.
- **`Payment` and `PaymentAllocation` kept as two tables from day one**, even though Phase 4's UI only ever creates one allocation per payment — this was already the locked Phase 0 design (ARCHITECTURE.md §5's "many-to-many via allocation"), and building the simpler 1:1 shape now would mean a breaking migration later when AR settlement (one payment covering several invoices) is eventually needed. The extra join costs nothing today.
- **Package purchase does not gate on payment** — `PatientPackage.status` starts `active` immediately, independent of whether its linked Charge has been invoiced/paid yet. This mirrors how a Prescription is usable the moment it's issued, regardless of billing status, and is the direct consequence of spec.md §33's Charge/Invoice separation: clinical/operational activity and revenue-cycle status are deliberately decoupled. A stricter "no session usable until paid" policy was considered and rejected as a hardcoded business rule spec.md §92 explicitly forbids baking in without a configuration mechanism — if a clinic wants that gate, it belongs in Settings, not application logic, and isn't built until a real need names it.
- **Tax uniqueness enforced at the service layer, not a DB constraint** — `TaxRule.serviceId` is nullable (null = org-wide default), and Postgres treats NULL as distinct in a unique index, which is the exact bug already hit once with `NumberSequence` in Phase 1. Rather than repeat the `COALESCE(..., sentinel)` workaround for a low-volume, admin-only config table, uniqueness ("one default, one rule per service") is a check-before-insert in the service function — an intentionally simpler tradeoff than the Phase 1 fix, appropriate because `TaxRule` writes are rare and never concurrent in the way `NumberSequence` increments are.
- **Automatic clinical consumption hooks into the billing engine, not CPOE** — spec.md §44 says "completing the procedure should generate stock consumption," and the natural reading is a CPOE `ClinicalOrder` completion event. But Phase 3 deliberately left `ProcedureOrderDetail.procedureName` as free text with no `serviceId` link, and Phase 4 deliberately deferred automatic procedure-charge generation (procedures are billed as ad-hoc POS charges with a manually-picked Service). Reopening either of those decisions just to wire consumption would have meant non-trivial rework of two already-shipped, already-tested phases. Hooking into `Charge` creation instead — which already carries `serviceId` for exactly this kind of lookup — covers every path a service can be billed through (automatic or ad-hoc) with zero changes to Phase 3/4 code, at the cost of consumption technically firing at "billed" rather than strictly "procedure completed." Given Phase 4 already made billing-timing calls balancing correctness against reopening prior phases (`EncounterCompleted` vs `EncounterFinalized`), this is a consistent continuation of that same discipline, not a new pattern.
- **FEFO implemented as real batch-walking allocation, not a single-oldest-batch shortcut** — spec.md §42's "use FEFO where appropriate" could be read as just sorting by expiry date, but a consumption request can legitimately span multiple batches (e.g. 12 units needed, only 8 remain in the earliest-expiring batch). `consumeStock()` walks every available batch in expiry order, taking what it can from each until the requested quantity is satisfied or stock runs out — the latter case throwing rather than partially consuming, so a Charge is never left half-fulfilled against inventory.
- **Stock transfers use their own request/complete workflow, not raw ledger entries** — spec.md names "Transfers" as its own Phase 5 deliverable, distinct from the ledger's `transfer_in`/`transfer_out` transaction types (which are the mechanism, not the workflow). A `StockTransfer` row tracks the request (who, when, pending/in_transit/completed/cancelled) independent of the ledger pair it eventually produces — matching the same request-then-fulfill shape already used for Purchase Requests and Refunds, rather than exposing raw ledger-entry creation as a user-facing action anywhere in the product.
- **No separate `unearned_revenue_ledger` table, despite one being named in the Phase 5 forward-schema note** — package deferred revenue is just an ordinary liability-type `ChartOfAccount` ("Unearned Revenue", seeded code 2200) and ordinary `Journal`/`JournalLine` postings against it, the same as every other account. A dedicated ledger table would only duplicate what `journal_line` already provides (a full, queryable posting history per account) with no behavioral difference — the forward-schema note pre-dated this session's actual design work on the posting service and named a table shape that turned out not to be needed once the general-purpose journal model existed. `getJournal()`/`listJournals(session, { referenceType: "patient_package_session" })` already gives the equivalent of a purpose-built ledger view.
- **`PostingIntent` is a fixed 14-value taxonomy, not a free-form string** — spec.md §55's posting examples name a small, closed set of accounting concepts (a payment tender, AR, revenue, tax payable, unearned revenue, inventory, AP, a default expense bucket); every `AccountMapping.intent` and every `resolveAccountId()` call site is typed against this union (`accounting/schemas.ts`), so a typo'd intent string is a compile-time error, not a silent no-op mapping lookup that resolves to nothing at runtime.
- **Sync vs. async posting decided per-trigger, not uniformly**: the six cross-domain triggers (Invoice/Payment/Refund/GoodsReceipt/SupplierPayment/PackageSession) post via the existing outbox pattern — asynchronous, after the triggering transaction commits, so a missing account-mapping configuration never blocks a clinical/revenue/inventory action (a posting failure just leaves the outbox event `failed` for retry). Expense creation and Manual Journal entry post synchronously in the same transaction as the row itself, since both are direct, single-purpose accountant actions where the user is watching the form and expects immediate confirmation the posting succeeded — there's no "other domain" whose availability needs protecting from accounting configuration gaps the way there is for a clinical charge or a goods receipt.
- **Package-vs-non-package revenue split on invoice issue uses proportional discount allocation, not a hard line-item split** — `postInvoiceIssued()` computes `packageSubtotal`/`otherSubtotal` from the invoice's lines (via each line's `Charge.sourceType`), then allocates the invoice's single document-level discount across both buckets in proportion to their share of the pre-discount subtotal, so `revenueAmount + unearnedAmount + discount = subtotal` exactly and the journal balances by construction even when a single invoice mixes a package purchase with ordinary consultation charges (a realistic POS scenario, not a hypothetical). Refunds do not attempt the mirror-image split (see Known Issues) — booked against generic `revenue`, a documented simplification rather than an oversight.
- **Financial reports are computed with one raw `$queryRaw` per report, not layered Prisma aggregate calls** — Trial Balance/Income Statement/Balance Sheet all share a single `accountBalances()` helper that does a `GROUP BY account_id` join with type-aware sign handling in one round trip; Prisma's query builder can't express "debit-normal vs. credit-normal sign flip based on the account's own `type` column" without either N+1 queries (one aggregate per account) or pulling every `journal_line` row into the app and summing in JS. Raw SQL here is the documented, reviewed exception SECURITY.md §6 allows ("raw SQL is a reviewed exception, never default") — parameterized via `Prisma.sql` template fragments throughout, never string-concatenated.
- **HR, Payroll, and Assets kept as three separate domains** (`src/lib/domains/hr/*`, `payroll/*`, `assets/*`), matching ARCHITECTURE.md §2's domain map exactly as it was scaffolded back in Phase 0 — `hr` owns Employee/Attendance/Leave, `payroll` owns PayrollRun/CommissionRule/CommissionAccrual (commission lives with payroll since it's a payroll input, not an HR-record concern), `assets` stands alone. This is a finer split than, say, billing's single domain folder, but it was the pre-committed plan and nothing about this phase's actual coupling argued for merging them.
- **Commission accrual is a pure operational record with no GL posting of its own** — a `CommissionAccrual` row never touches `journal_line` directly; it only ever reaches the ledger indirectly, folded into a `PayrollRunLine.commission` figure at payroll time, which *is* posted (as part of the combined Salary Expense line). Considered and rejected: posting each accrual immediately as it's earned (e.g. `Dr Commission Expense / Cr Commission Payable`) — spec.md §55's only payroll example is the single combined `Debit Salary Expense / Credit Payroll Payable` posting, and inventing a second, finer-grained commission-specific GL flow wasn't asked for and would have meant either double-counting at payroll time or a reconciliation step nothing in spec names.
- **`listEmployeeDirectory()` deliberately bypasses `payroll.view`** — a name-only `{id, firstName, lastName}` projection used purely for assignment pickers (e.g. Assets' "assigned employee" dropdown, Providers' "link employee" dropdown), gated on nothing beyond authentication, mirroring the `listAccessibleBranches()` precedent from Phase 4. The alternative — granting `payroll.view` (which exposes salary, leave, and attendance data) to every role that merely needs to pick a name from a list, like Inventory Manager assigning an asset — would have been a much larger, unjustified permission expansion just to solve a dropdown. This is the field-level-projection discipline from SECURITY.md §2 ("two different projection functions returning different field sets from the same row"), applied to a new case.
- **Doctor-order-intent and lab-execution-reality kept as two deliberately separate tables, not a rework of Phase 3's CPOE model** — `ClinicalOrder`/`LabOrderDetail` (Phase 3, free-text `testName`) capture what the doctor asked for; `LabOrderTest` (this phase, catalog-referenced, priced, resulted) capture what the lab actually ran and billed. Considered and rejected: reworking the Phase 3 CPOE lab-order dialog to require picking catalog tests directly at order time — that would force every doctor to know exact lab codes at the point of ordering (unrealistic; doctors write "CBC, lytes," lab staff translate that into billable codes), and would mean reopening and re-testing an already-shipped, already-verified Phase 3 UI flow for a benefit (skipping one translation step) spec.md §28 never asks for. The same "don't reopen a working, tested prior-phase flow to reach a marginal deeper hook" reasoning Phase 5 already applied when it hung automatic consumption off the billing engine rather than CPOE.
- **Billing fires at test-assignment time, not at result-verification time** — a real clinic bills for a lab test once it's accessioned and being processed (the resource commitment has been made), not once results come back, matching how `EncounterCompleted` bills at the consultation event rather than at note-finalization. A specimen later rejected still leaves its Charge in place — voiding it, if warranted, is the existing `charge.void` path every other charge already uses, not a new lab-specific reversal mechanism.
- **A panel's Charge attaches to only its first member `LabOrderTest` row** (`chargeId` is `@unique` on the table, by design) — the panel is billed once as a single line, not once per member test, so the other N−1 members correctly carry no `chargeId` of their own; `labPanelId` is what groups them for display, not the charge relation.
- **`Medication` is a 1:1 companion to `Product`, not a parallel item master** — `Medication.productId` is a unique FK, and every stock/batch/cost/price concern is inherited from `Product` wholesale rather than duplicated onto `Medication`. Considered and rejected: a standalone pharmacy item table with its own SKU/pricing/stock columns — that would fork inventory into two disconnected systems (a pharmacy product wouldn't show up in general inventory reports, low-stock alerts, or the procurement chain without duplicate wiring), the exact kind of parallel-system drift `CommissionRule` already avoided by referencing `Product` directly in Phase 7.
- **Dispensing's inventory-reduction/billing/history triple is synchronous, in one transaction — not fired as a domain event**, the same reasoning already applied to Phase 8's `assignTests()` billing (also synchronous, not event-driven): a pharmacist's "Dispense" click is a single, direct, permission-gated user action expecting immediate confirmation all three things succeeded together, not a fire-and-forget trigger with a separate async subscriber. Considered and rejected: firing a `MedicationDispensed` event and letting outbox handlers do the stock/billing/history work — that would reintroduce exactly the "a missing account mapping shouldn't block the triggering action" tradeoff the async outbox pattern exists for (see Phase 6's sync-vs-async split), which doesn't apply here since there's no analogous "acceptable to fail and retry later" step in this flow — a dispensed medication with no corresponding stock reduction or charge would be a worse failure mode than the whole action failing atomically.
- **`consumeStock()` gained an optional `transactionType` parameter rather than a second consumption function** — Pharmacy dispensing needed the identical FEFO batch-walking algorithm Phase 5 already built for automatic clinical consumption, differing only in which ledger transaction-type label the resulting entries carry (`"dispensing"` vs. the existing default `"treatment_consumption"`). Duplicating the FEFO walk into a second `dispenseStock()` function would have meant two copies of the same allocation algorithm to keep in sync; the one-line optional-parameter extension keeps every existing caller's behavior byte-for-byte unchanged (the parameter defaults to the original meaning) while giving Pharmacy its own distinguishable ledger label.
- **Estimated patient-vs-payor responsibility is invoice-level informational data, not a literal GL sub-ledger split** — `postInvoiceIssued()` is deliberately unchanged this phase: it still posts one combined `Dr AR (total) / Cr Revenue+Tax+Unearned`, exactly as Phase 6 built it, rather than splitting AR into a "patient AR" sub-account and a "payor AR" sub-account. Considered and rejected: adding a new `accounts_receivable_payor` PostingIntent and conditionally branching `postInvoiceIssued()`'s AR line whenever an invoice carries a payor. Rejected because the combined AR debit is already correct and balanced regardless of who ultimately pays (the same total is owed either way), and splitting it would mean touching Phase 6's already-tested, already-verified posting function for a benefit — a queryable patient-vs-payor AR aging split — that a real deployment hasn't asked for yet. `estimatedPatientResponsibility`/`estimatedPayorResponsibility` on `Invoice` give the same information for display/collections purposes without the GL risk; revisit if AR aging-by-payor becomes a real reporting need.
- **Remittance reuses the ordinary Payment/PaymentAllocation path rather than a parallel claims-specific ledger** — `recordRemittance()` creates a real `Payment` (method `insurance`) exactly like any POS-recorded tender, fires the same `PaymentReceived` event, and gets the same accounting/commission treatment automatically. Considered and rejected: a dedicated `Remittance` table with its own posting function. Rejected because a remittance genuinely *is* a payment — modeling it separately would mean either double-bookkeeping (a Remittance row plus a Payment row referencing the same money) or reimplementing invoice-balance/status recalculation a second time, both of which contradict the "one writer per concept" discipline this build has held since Phase 4's centralized billing engine.
- **The cashier-session requirement is bypassed for remittances, not loosened globally** — `recordPayment()` (POS) still requires an open cashier session belonging to the recording user; `recordRemittance()` (claims) does not, since it creates the `Payment` row directly rather than calling through `recordPayment()`. This is a deliberate fork at the point the two flows' real-world preconditions diverge (a POS tender happens at a physical register; a remittance is a back-office bank reconciliation), not a general weakening of the cashier-session control — POS-recorded payments are completely unaffected.
- **`ClaimSubmissionAdapter` is a real interface with one honest implementation, not a comment describing a future one** — spec.md §39 explicitly asks to "create adapters for future country-specific integrations." Considered and rejected: skipping the interface and just setting `status: "submitted"` directly in `submitClaim()`, with a comment noting where a real integration would go. Rejected because spec names the adapter pattern specifically, and the actual code cost of a one-method interface plus a single manual implementation is trivial — the same "build the real seam, not a comment about a seam" standard already applied to every registered-but-no-op domain event since Phase 2 (`PatientRegistered`, `AppointmentBooked`, `EncounterFinalized`, ...).
- **`Claim` stores `branchId` directly, unlike the leaner clinical-execution tables (`LabOrderTest`, `ImagingOrder`) that derive it from a parent** — `Claim` sits in the billing/revenue-cycle family (`Invoice`, `Payment`, `Charge`, `Refund` all store `branchId` directly), not the clinical-execution family, so it follows its siblings' convention rather than the leaner one, for consistency with the tables it's actually adjacent to and queried alongside.
- **`PatientPortalAccount`/`PatientPortalSession` are separate tables from `User`/`Session`, not a shared table with a discriminator column** — considered and rejected: adding an `accountType`/`role` column to the existing `User`/`Session` pair and treating a patient portal login as "just another kind of user." Rejected because the two auth contexts have genuinely different authorization models (RBAC permissions vs. "this session may only ever see one specific patient's data") and different lifecycles (staff accounts are admin-provisioned with roles; portal accounts are provisioned per-patient with none) — collapsing them into one table risks a permission-check bug in one context accidentally granting access in the other, a category of mistake a fully separate table makes structurally impossible, not just unlikely. The two-cookie split (`his_session` vs `his_portal_session`) is the other half of this same isolation guarantee.
- **Online Booking's public entry point reuses `bookAppointment()`'s race-condition machinery by direct code reuse (exported helpers), not by re-deriving it** — `translateBookingError`/`assertNoLeaveConflict` were made exported rather than re-implemented in the new `booking` domain, and `submitPublicBooking()` writes to the exact same `appointment` table through the exact same DB exclusion constraint Phase 2 built and verified. Considered and rejected: giving public bookings their own staging/holding table reconciled later, to reduce the public path's blast radius. Rejected because the DB constraint is already the correct, already-proven safety mechanism — adding a second, different code path for "book but from the internet" would mean maintaining two implementations of the one thing (conflict-free scheduling) that most needs to be provably correct, exactly the risk `translateBookingError`'s own doc comment already warns about for the staff path.
- **Online Booking's patient-matching is exact-mobile-only, deliberately simpler than staff registration's fuzzy duplicate detection** — Phase 2's `registerPatient()` duplicate check surfaces "maybe" matches (similar name + DOB, etc.) for a human to interactively resolve with an override reason. A public, unattended flow has no human in that loop to make that judgment call, so offering a "maybe" match would mean either silently picking one (risking merging two different people's records) or blocking the booking entirely (defeating the point of self-service). Exact-match on a normally-unique field (mobile number) is the safe subset of that logic that doesn't need a human referee.
- **Communication engine variable substitution is a flat `Record<string, string>`, not a typed-per-template schema** — every template's `{{variable}}` placeholders are just string keys; `renderTemplate()` leaves an unresolved `{{key}}` untouched if the caller doesn't supply it (verified in the integration script that this never actually happens for a correctly-wired caller) rather than throwing. Considered and rejected: a discriminated-union input type keyed by `templateKey`, so TypeScript would catch a caller forgetting a required variable. Rejected as premature type machinery for 8 templates with 2-5 variables each — revisit if the template catalog grows enough that a missed variable becomes a recurring real bug rather than a hypothetical one.
- **`ClaimItem` references a real encounter `Diagnosis` row (Phase 3), not a bare `DiagnosisCode` catalog entry** — a claim line should cite which of the patient's *actual documented* diagnoses justifies it, not an untethered code. This also means a claim can never cite a diagnosis the patient doesn't actually have on record, a correctness property a direct `DiagnosisCode` reference wouldn't guarantee.
- **The `Setting` table's first real consumer is a boolean feature flag, not a broader settings framework** — `getSetting`/`setSetting` are intentionally generic (any JSON-serializable value, any string key), but Phase 9 only actually exercises one key (`pharmacy_enabled`). No settings-admin UI for arbitrary keys was built — just the one Pharmacy toggle spec.md §29 explicitly asks for — since building a general key management UI ahead of a second real settings need would be speculative infrastructure this build has consistently avoided (e.g. the tax-jurisdiction-selection deferral in Phase 4, the critical-value-band deferral in Phase 8).
- **`ImagingOrder` is a real 1:1 with `ClinicalOrder`, deliberately not a one-to-many the way `LabOrderTest` is** — considered and rejected: mirroring Lab's panel-expansion shape (one order fans out into several structured lines) for symmetry with Phase 8's precedent. Rejected because it would model something that doesn't exist in real radiology workflow: a doctor orders one study per CPOE order ("Chest X-Ray," "Abdominal Ultrasound" are two separate orders), never a single order bundling several imaging studies the way "CBC, lytes" bundles several lab analytes into one free-text order. Copying Lab's shape here would have added complexity (a fan-out relation, a "how many of N assigned/verified" completion check) modeling a scenario that never occurs, purely for consistency with a different phase's genuinely different problem — the same "don't force a precedent to fit where the underlying reality differs" judgment call this build has made before (e.g. Phase 9's dispensing-partial-fills shape differs from Lab's panel shape too, for the same reason: different real-world cardinality).
- **PACS integration modeled as two nullable, currently-unused fields (`accessionNumber`, `externalImageUrl`), not a stub file-storage subsystem** — spec.md §30 explicitly instructs "prepare integration architecture for future PACS. Do not attempt to build a PACS from scratch." Considered and rejected: building even a minimal image-upload/storage flow now, reasoning a real deployment will eventually need *something*. Rejected because a real PACS integration's actual contract (DICOM C-STORE, a vendor's REST API, a viewer redirect URL) isn't knowable without a real vendor target, and building speculative storage now risks it being wrong-shaped for whatever real integration eventually lands — the same "don't build ahead of a concrete need" discipline already applied to file storage everywhere else in this codebase (`EmployeeDocument`, lab records, medications), just with spec explicitly naming the deferral this time instead of this build inferring it.
- **Every Phase 13 permission gate reuses an existing `resource.action` code — zero new permissions were added** — Dashboards/Reports map onto the view permission each domain already exercises (`appointment.view`, `encounter.view`, `accounting.view`, `invoice.view`, `claim.create`, `inventory.view`, `payroll.view`), and the Management Dashboard section reuses `reports.export` (already granted to exactly the management-tier roles) rather than inventing a `dashboard.view`. Considered and rejected: a dedicated `report.view`/`dashboard.view` permission per category. Rejected because it would duplicate an authorization decision ("can this role see this domain's data") the seed already makes once per domain, and because SECURITY.md §2's capability-based model means *any* role holding the right domain permission should see that domain's report without a second, parallel grant to remember to keep in sync.
- **`reports.export`, reserved since Phase 1 with the description "Export reports" and never checked by any real code path until now, gates CSV export specifically — separate from viewing** — a role can hold a category's view permission (see a report on screen) without holding `reports.export` (download it as a file), matching the existing seed grants exactly (Doctor/Nurse/Lab Tech/etc. can view what they're scoped to but not export; Clinic Manager/Accountant/HR Manager/Admins can do both). This is the fifth "permission/sequence/event reserved since an early phase, finally wired for real" instance in this build, after `Provider.employeeId`, `EmployeeLeaveApproved`, `LabResultFinalized`, and the `LAB`/`CLM` sequences.
- **CSV export required the codebase's first real `/api/*` Route Handler** — every prior phase's mutations went through Server Actions (API.md's own Status paragraph called the Route Handler layer "speculative"). A file download needs a real, browser-navigable URL with `Content-Disposition`/`Content-Type` headers a Server Action can't produce; `src/app/api/reports/export/route.ts` is a genuine, motivated first use, not reaching for the pattern out of habit. It sits behind the same staff-session `proxy.ts` check as every dashboard page (no new public/portal route class was needed).
- **KPI trend charts are plain CSS bars, not a new charting-library dependency** — considered and rejected: adding `recharts` (the natural shadcn/ui pairing). Rejected for six simple monthly bars with no need for zoom/tooltips/multi-series interaction — the same "no unnecessary complexity" call already made for the outbox dispatcher (no background job runner, ARCHITECTURE.md §15) and the communication engine (no fake scheduler, ARCHITECTURE.md §13). Revisit if a real deployment needs richer visualization a CSS bar genuinely can't express.
- **Dashboards are permission-gated sections on one page, not one page per role** — considered and rejected: a `role`-keyed dashboard router (Receptionist → `/dashboard/reception`, Doctor → `/dashboard/doctor`, ...). Rejected because roles aren't the actual authorization unit anywhere else in this codebase (SECURITY.md §2's whole point is capability-based permissions, not role-name branching) — a user holding multiple qualifying permission sets (e.g. Clinic Manager, who has both `reports.export` and `accounting.view`) should see both the Management and Finance sections on one page, not be forced to pick a single role-shaped view.
- **Global Search (spec.md §66) and the master-data bulk Import/Export workflow (spec.md §83) are deliberately excluded from Phase 13**, following the same discipline Phase 12 already applied to Lead CRM: spec.md's literal numbered "PHASE 13 — ANALYTICS" Implement list names exactly four things (Dashboards, Reports, KPIs, Exports); neither §66 nor §83 is on it, despite sitting in the same numbered-sections neighborhood as §65 Reports & Analytics. Both remain genuinely unassigned to any phase's explicit list, tracked in Next Actions rather than built speculatively into a phase that didn't ask for them.
- **Two functions were extracted from existing async/DB-coupled service functions into standalone pure functions specifically to make them unit-testable, not for any other refactoring reason** — `computeInvoicePostingSplit()` (out of `postInvoiceIssued`) and `allocateFefo()` (out of `consumeStock`). Considered and rejected: leaving them inline and testing them only via integration tests against the real DB. Rejected because both are genuinely pure decision logic with several real boundary conditions (a zero subtotal, a discount exceeding one bucket, an empty batch list) that are far cheaper and more precisely expressible as unit tests than as DB-fixture-dependent integration tests — the same "extract for testability when the underlying logic is genuinely pure" judgment call, applied for the first time in this build specifically because Phase 14 is the phase that finally needed real test coverage to justify it.
- **The automated test suite runs against the real development database for its integration tests, not a mocked Prisma client or an ephemeral test database** — considered and rejected: mocking `db` with a library like `prisma-mock`, or spinning up a disposable Postgres via Testcontainers. Rejected because this build's `db` client, DB-level constraints (the exclusion constraint, the balance trigger), and Prisma's own query generation are themselves exactly what needs verifying for the two DB-coupled tests that exist — a mock would test that the mock behaves as configured, not that the actual constraint fires; and this project's Supabase-hosted database is the only Postgres instance this build has ever run against (see DEPLOYMENT.md's note on why `migrate dev`'s shadow-DB approach doesn't work here either), so introducing a second, different Postgres just for tests would test against an environment nothing else in this project has ever exercised. The tradeoff accepted: integration tests are slower and require real connectivity, mitigated by keeping the integration-test count small (5, not dozens) and self-cleaning.
- **`server-only` is aliased at the vitest-config level to a permanent stub file (`test/server-only-stub.ts`), not worked around per-test** — every domain service file begins `import "server-only"`, which only Next.js's own bundler resolves specially; running the same files under vitest's plain Node environment would otherwise throw on every single import. This is the config-level, permanent equivalent of the temporary `node_modules/server-only` shim every phase's standalone tsx integration-verification script has manually recreated and deleted since Phase 9 — Phase 14 is the first phase to need that workaround to persist across sessions rather than being reconstructed by hand each time.
- **DB privilege hardening was documented, not silently dropped or faked** — see Completed/Known Issues above. Considered and rejected: creating the new low-privilege role and rotating `DATABASE_URL` autonomously, since this phase's mandate is "harden," and the fix is well-understood and low-risk in the abstract. Rejected because rotating live database credentials the running application depends on is exactly the class of action this build's standing safety discipline treats as needing explicit user confirmation first (a wrong grant is a genuine "the app stops working" failure mode) — writing down the precise, actionable fix is the responsible version of "harden this," not a substitute for actually doing it once the user confirms.
- **No axe-core or equivalent automated accessibility tool was added as a dependency** — considered and rejected, matching the same "no unnecessary dependency" reasoning already applied to not adding a charting library in Phase 13. A manual, targeted spot-check (label association, accessible naming, responsive overflow) caught what it caught and is documented as exactly that scope, not dressed up as a full audit — installing a real a11y tool is a legitimate, low-cost future addition if a deeper audit becomes a real need, tracked in Next Actions rather than added speculatively this phase.
- **Imaging scheduling reuses `Room` (existing since Phase 1) but not the `Appointment`/booking-conflict machinery** — an `ImagingOrder` optionally references a `Room` for display/planning purposes, the same master-data table Provider Scheduling already uses, but does not create an `Appointment` row or participate in the Phase 2 double-booking exclusion constraint. Considered and rejected: modeling a scheduled imaging study as a special kind of Appointment, to get double-booking protection for free. Rejected because Appointment is tightly coupled to the patient-facing booking/check-in/queue workflow (status lifecycle, queue tokens, reschedule-linking) that doesn't apply to a radiology study's internal scheduling, and forcing that coupling to borrow one constraint would have meant carrying a lot of irrelevant Appointment machinery along with it.
