# PRODUCTION_READINESS.md

P2 Batch 7 (§23): **not a scaling pass.** This inspects whether specific, named architectural decisions would break under roughly 200+ staff users, and documents what's acceptable now versus what needs real production-readiness work later. No code changes were made for this section — §9/§22's work (see PERFORMANCE_NOTES.md/PERFORMANCE_BASELINE.md) fixed what was safe to fix; this section is assessment only, per P2.md §23's own explicit instruction, with two exceptions: a stale documentation bug (DEPLOYMENT.md/.env.example still named the wrong Supabase pooler port) was corrected while investigating this section, since leaving it would actively mislead a future deployment toward repeating a real outage this project already had.

No microservices, no Redis, no message broker — none of the findings below call for any of those, and P2.md §23 explicitly rules them out regardless.

## Database connection usage / Prisma connection configuration

**What exists**: `src/lib/db.ts` constructs one `pg.Pool`-backed `PrismaClient` per process, explicitly capped at `max: 3` connections, cached across hot-reloads and warm serverless invocations via `globalThis`. The cap and the caching are both deliberate, documented decisions (see the file's own comment): a serverless deployment (Vercel functions) can have many concurrently-running function instances, each opening its own pool — an uncapped or default-sized (10) pool per instance would multiply fast against Supabase's own pooler connection ceiling.

**Acceptable now**: the cap is real and load-tested indirectly — this whole P0-P2 engagement's own integration suite has run hundreds of times against this exact configuration, including full-suite runs with 30-50+ files exercising real concurrent-ish write paths. The math (`max: 3` × N concurrent function instances) genuinely bounds worst-case connection count from this application's side; it is not a number picked without a specific failure mode in mind.

**Needs attention before/around 200+ staff**: `max: 3` was sized for the LOW end of expected concurrency (this project has run, until now, against a handful of real or synthetic users at a time). At 200+ staff with meaningfully overlapping usage (a busy multi-branch clinic's shift-change hour, for example), the *number of concurrent serverless function instances* Vercel spins up is what actually determines total connection count, not the per-instance cap — and that number isn't something this codebase controls directly. This needs a real number from Vercel's own concurrency behavior under the deployment's actual traffic pattern, cross-checked against the Supabase project's own pooler connection ceiling (visible in the Supabase dashboard, not this codebase) — a load test, not a code change, is the right next step here. If that cross-check shows the ceiling is close, the lever to pull is Supabase's own pooler-side connection limit (a plan/configuration change), not a code change to this cap.

## Supabase pooler usage

**What exists, and a real bug fixed while investigating this section**: this application must connect through Supabase's Supavisor pooler in **transaction mode** (port 6543, `pgbouncer=true`) — never session mode (port 5432). Session mode holds one real Postgres connection per pooled client for that client's entire lifetime; under serverless concurrency, many short-lived function instances each holding a session-mode connection exhausts the pooler's own cap fast. **This is not a hypothetical risk — it caused a real production `EMAXCONNSESSION` ("max clients reached in session mode") outage** earlier in this engagement, fixed by correcting the deployed `DATABASE_URL` to transaction mode.

`DEPLOYMENT.md`'s own "Environment Variables" documentation and `.env.example` had drifted back to describing port 5432 as correct — both corrected in this batch (not a code change, a documentation-accuracy fix) so a future redeploy or environment rebuild doesn't silently reintroduce the exact bug this project already paid for once. `src/lib/db.ts`'s own comment already explained *why* transaction mode is required; the drift was specifically in the deployment-facing docs a person provisioning a new environment would actually read.

**Acceptable now**: the currently-deployed configuration is correct (transaction mode), verified live during this engagement's own earlier troubleshooting of the outage above.

**Needs attention before 200+ staff**: none identified beyond keeping the corrected documentation from drifting again — transaction-mode pooling is the standard, correct choice for serverless at any scale this system is likely to reach without a fundamentally different deployment topology.

## Synchronous outbox dispatch behavior

**What exists**: every write that produces a domain event (`generateInvoice`, `recordPayment`, `recordAdjustment`, and every other write path with real cross-cutting effects — accounting postings, commission accruals, etc.) calls `writeOutboxEvent` inside its own transaction, then, **after that transaction commits**, calls `await dispatchPendingOutboxEvents(organizationId)` inline, in the same request, before returning a response. This is the "fast, primary delivery path" `outbox.ts`'s own comments describe — by design, not an oversight: it makes the common case (an event's handler runs and completes within the same request that created it) fast and simple, with no separate worker process needed.

Two real safety nets already exist if this synchronous call is slow, fails, or the process is killed mid-handler: (1) the *next* write to the *same organization* will attempt dispatch again and pick up anything still `pending`/`failed`-and-due; (2) a periodic, organization-agnostic sweep (`processPendingOutboxEvents`, scheduled via Vercel Cron, `/api/cron/outbox-sweep`) recovers stuck `processing` events and re-attempts due `failed` ones, independent of any specific write happening.

**Acceptable now**: correctness is not at risk — every handler is required to be idempotent (documented and verified in `dispatchBatch`'s own comment), so a slow or retried dispatch never double-processes. At this project's actual current scale, the inline dispatch adds a small, bounded amount of latency to each write (a handful of extra DB round trips for whatever handlers that event type has), not a correctness problem.

**Needs attention before/around 200+ staff, and this is the most concrete finding in this document**: two compounding issues.

1. **Latency**: under concurrent write load, every write request now pays for its own event's handler execution synchronously — a request that used to be "one transaction" is now "one transaction, then N more DB round trips before the user gets a response." PERFORMANCE_BASELINE.md's own measurements show individual round trips to this environment's Postgres instance can take anywhere from ~200ms to multiple seconds; a write whose handler chain needs 3-4 more round trips can meaningfully lengthen the user-perceived response time, and does so *more*, not less, as concurrent load rises (more contention on the same capped connection pool described above).
2. **The recovery-sweep fallback is currently only scheduled once daily**, a real, already-documented constraint (`DEPLOYMENT.md`'s "Outbox Sweep Scheduling") — the project runs on Vercel's Hobby tier, which rejects any cron schedule more frequent than daily. That document already recommends upgrading to a paid tier and restoring 5-minute sweep precision; this assessment agrees and adds: at 200+ staff, relying on "some other write to the same org happens to retry a stuck event" as the *only* sub-24-hour recovery path is not a robust guarantee, especially for a financial/clinical system. **Upgrading past the Hobby tier and restoring frequent sweep scheduling should happen before, not after, staff count grows meaningfully** — this is cheap (a plan change plus reverting one line in `vercel.json`) and directly closes a real gap, unlike the connection-pool question above, which needs a load test before any specific number can be recommended.

Neither of these calls for a message broker or a separate worker fleet — the existing pattern (inline fast path + periodic sweep fallback) is architecturally sound for a modular monolith at this scale; it needs its scheduling restored to what it was designed for, not a redesign.

## Long transactions

**What exists**: 13 domain files widen Prisma's default interactive-transaction limits (2000ms to acquire + start, 5000ms to run) to `{ timeout: 20_000, maxWait: 10_000 }` — a large, deliberate, and *already necessary* change, not headroom added speculatively. Every one of these was widened because this environment's real Supabase-pooler round-trip latency, combined with a transaction doing several sequential writes (a common shape: `nextNumber()`'s own nested transaction for a sequence value, then one `create` per line/item in a loop, e.g. `generateInvoice`'s per-charge `invoiceLine.create`), genuinely exceeded the 5-second default during this engagement's own real test runs — this is empirical, not defensive.

**Acceptable now**: widening the timeout is a legitimate, working fix for what it addresses (a transaction that's correct but slow finishing before Prisma gives up on it) — every one of these paths is exercised repeatedly by the integration suite and works.

**Needs attention before/around 200+ staff**: a transaction held open for up to 20 seconds, under a connection pool capped at 3 per instance, is exactly the shape of thing that causes queuing under concurrent load — if 3 concurrent writes to the same serverless instance each need up to 20 seconds of transaction time, a 4th concurrent write to that instance queues behind them. The *timeout widening* was the right fix for correctness (a transaction that used to fail outright now succeeds); it does not address the *underlying* per-row sequential-write pattern that makes these transactions slow in the first place. The real fix, when this becomes a measured problem rather than a theoretical one, is the same shape P2 Batch 3 already applied to commission accruals: batch the per-row `create` calls into a single `createMany` where the rows don't need each other's generated ids, and prefetch/batch any per-row lookups instead of looping `await` inside the transaction. This is a query-shape fix, not an infrastructure one, and should be done incrementally, guided by which specific write paths actually show contention under real load — not speculatively rewritten now.

## Excessive sequential queries

**Acceptable now, largely already addressed**: P2 Batch 3 found and fixed the worst offender (commission accrual's ~90-query-per-invoice N+1) and the invoice tax-rate N+1; P2 Batch 7 (this batch, §9) found and fixed two report-level redundant re-queries. PERFORMANCE_BASELINE.md's real measurements show every screen measured uses either a single query, a small parallel fan-out (`Promise.all` of independent queries — Patient 360's 25 queries are this shape, not sequential), or a bounded `groupBy`/`aggregate` — no screen measured chains queries sequentially per row of a result set, with the one documented exception below.

**Needs attention, small and already scoped**: the near-expiry/expired-batch balance lookups in `inventory/stock.ts` (`listNearExpiryBatches`/`listExpiredBatches`) call `getBalance` once per batch found, via `Promise.all` (parallel, not literally sequential, but still N+1 in query *count*) — found via PERFORMANCE_BASELINE.md's real measurement, documented in PERFORMANCE_NOTES.md, not fixed this batch (bounded by a naturally small row count — near-expiry/expired batches, not the whole catalog — so it isn't the pattern likely to bite first at 200+ staff).

## Full-table scans

**Acceptable now**: P2 Batch 1 (§3) added 15 indexes specifically targeting real `WHERE`/`ORDER BY` column combinations that were previously unindexed (verified by grepping actual query usage, not guessed); P2 Batch 6 (§8) replaced every hard-capped or fully-unbounded list with real server-side pagination backed by those same indexes. No list or report reviewed in P2 Batches 6/7 scans an unindexed column or an unbounded row range. Nothing here needs attention before 200+ staff specifically — this was already the target of dedicated earlier work, not left for this section to discover.

## Polling loops

**None exist.** A repository-wide search for `setInterval`, timer-driven `fetch`, or a client-side polling `useEffect` found zero matches anywhere in `src/app` or `src/components` — every screen in this application is server-rendered per request/navigation, not client-polled. The one legitimate periodic job in the system is the outbox sweep cron discussed above, which is server-scheduled infrastructure, not a client polling loop. Nothing to address here at any user count.

## Unbounded lists

**Acceptable now, mostly already addressed**: P2 Batch 6 (§8) converted every major hard-capped or fully-unbounded list named in P2.md's own priority list to real `page`/`pageSize`/`totalCount`/`totalPages` pagination. A small number of narrower gaps were found and deliberately deferred during that batch, with reasoning already recorded in BACKLOG.md: Purchase Orders/Purchase Requests (real caps, not named in that batch's own scope) and the `cashFlow` report's inflow/outflow lists (bounded to the current month by this batch's §9 work, but with no row cap of its own within that month — see PERFORMANCE_NOTES.md). Neither is a 200-staff-specific risk on its own; both are already tracked.

## Repeated dashboard recomputation

**What exists**: `analytics/dashboards.ts`'s `getManagementDashboard`/`getFinanceDashboard`/`getReceptionDashboard`/`getDoctorDashboard` are computed live, from real rows, on every single request — no cached/stored aggregate, by explicit design (spec.md §92: "never fake dashboard statistics"). PERFORMANCE_BASELINE.md measured `getManagementDashboard` at 20-23 real queries per load, every one a bounded, indexed `count`/`aggregate`/`groupBy` — not a full-table scan, and not literally repeated computation of the *same* number twice within one request (that specific pattern was what this batch's §9 work fixed in the accounting statements, a different code path).

**Acceptable now**: at any request rate this project has actually run at, 20 fast indexed aggregates in parallel is not a real latency problem, and correctness (never showing a stale number) is a deliberate, named product requirement, not an oversight.

**Needs attention before/around 200+ staff, but the right fix depends on real usage data this project doesn't have yet**: 20+ queries *per dashboard load*, multiplied by however many staff have a dashboard open and however often each of them reloads/revisits it, is a real aggregate load number worth knowing before assuming it's fine — and "how often does staff actually reload the management dashboard" is a usage-pattern question, not something inferable from this codebase. If that number turns out to be high (e.g., a dashboard left open and auto-refreshing, which doesn't currently exist but could be added later), the correct fix is **not** a materialized view or Redis cache added speculatively (P2.md §23 rules out exactly this reflex) — it's establishing the actual read-vs-write ratio and staleness tolerance for each specific number first, since "revenue today" tolerating even a 60-second-stale cached value is a very different product decision than "outstanding cashier balance" needing to be exact — a decision for whoever owns that product tradeoff, not a default this assessment should set unilaterally.

## Summary: what to do before 200+ staff, in priority order

1. **Restore the outbox sweep's scheduling precision** (upgrade past Vercel's Hobby tier, revert `vercel.json`'s cron schedule) — cheap, already-documented, closes a real recovery-latency gap for a financial/clinical system. Highest priority because it's both cheap and already understood; no investigation needed, just a plan change.
2. **Load-test real concurrent-write behavior** against the current `max: 3` connection pool cap and Supabase's own pooler connection ceiling, using a traffic pattern representative of 200+ staff's actual overlap (shift-change peaks, not a flat average) — this is the one item here that genuinely needs new data this codebase can't produce on its own.
3. **Watch the widened-transaction write paths** (invoice generation, payment recording, and the 11 other files sharing the same pattern) for real contention once staff count grows — the fix, if and when it's needed, is batching per-row sequential creates the same way P2 Batch 3 already did for commission accruals, not a bigger timeout.
4. Everything else in this document is either already fine at this scale or already tracked in BACKLOG.md/PERFORMANCE_NOTES.md with no new action implied by this section.
