# SECURITY.md

Living reference for authentication, authorization, and security controls. Updated at the end of every phase.

## 1. Authentication

Hand-rolled, DB-backed session auth (BLUEPRINT.md §43 decision #1, approved). Rationale: full control over lockout/login-history/instant-revocation requirements (spec.md §6) without fighting a library's assumptions.

- Passwords hashed with **argon2id** (`argon2` package). Never logged, never returned in any API response, never stored in `audit_log.old_values`/`new_values` (password_hash is explicitly excluded from the audited-fields set for the `user` entity).
- Session: opaque random token (256-bit), stored hashed in `session.token_hash`, set as an `HttpOnly, Secure, SameSite=Lax` cookie. Session row carries `expires_at` and `revoked_at` — logout / admin-forced-logout sets `revoked_at`, checked on every request (this is why sessions are DB-backed, not stateless JWT).
- Failed login: increments `user.failed_login_count`; after a configurable threshold (default 5), sets `user.locked_until` (progressive backoff). Every attempt (success or failure) writes a `login_history` row.
- Password reset: single-use token (hashed at rest), short expiry (default 30 min), invalidates all existing sessions on successful reset.
- MFA: schema field (`user.mfa_enabled`) present, feature-flagged off for v1 (spec.md §6 — "optional future MFA/2FA").

**A second, genuinely separate auth context as of Phase 12** (spec.md §57's Patient Portal): `patient_portal_account`/`patient_portal_session` mirror every one of the above staff-session properties (argon2id hashing, opaque hashed session tokens, the same failed-attempt lockout mechanism, a distinct `HttpOnly`/`Secure`/`SameSite=Lax` cookie — `his_portal_session`, never `his_session`) but are structurally isolated tables, not a discriminator column on `user`/`session`. Staff-provisioned only (`enablePortalAccess()`, gated on `patient.edit`) — no public self-registration exists, since verifying a claimed identity before granting clinical-data access is a real safety concern. Missing relative to staff auth: a per-attempt `login_history` equivalent (see PROJECT_STATUS.md's Phase 12 Known Issues) and self-service password reset (staff-only via `resetPortalPassword()`, since there's no live email provider to deliver a reset link through — see the same Known Issues entry).

## 2. Authorization (RBAC)

Capability-based permissions (`resource.action` strings), stored as data in `permission`/`role`/`role_permission`/`user_role` — never hardcoded `if (role === 'doctor')` branching in application code. Single enforcement chokepoint:

```ts
can(session, "invoice.discount", { branchId, resourceOwnerId? }): boolean
```

Enforced at three layers, each independent (no layer trusts the one above it):
1. **Middleware** — route-level default-deny; unauthenticated or unauthorized requests never reach a handler.
2. **Service layer** — every domain service function checks the specific permission(s) its operation requires before mutating anything.
3. **Query-projection layer** — DTOs are permission-aware; e.g., `getPatientForReception()` and `getPatientForClinician()` are two different projection functions returning different field sets from the same `patient` row, never a single "return everything, hide in UI" function. This is the field-level scoping correction from the blueprint review (reception must not incidentally receive clinical-note fields in an API payload).

Branch scoping is a second, orthogonal dimension: a role grants *what* a user can do; `user_branch_access` grants *where*. `can()` takes both into account.

## 3. Default Roles (seed data, spec.md §7)

Super Admin, Organization Administrator, Clinic Manager, Receptionist, Doctor, Nurse, Laboratory Technician, Pharmacist, Radiology Technician, Cashier, Accountant, HR Manager, Inventory Manager. Super Admin is the only role with an implicit all-permissions bypass — still fully audit-logged.

## 5. Audit Architecture (spec.md §62 vs §63 — two distinct logs)

- **`audit_log`** — mutation audit. Written by a shared data-access hook, not scattered manual calls, so it cannot be forgotten on new code paths. Captures user, timestamp, action, entity type/id, old/new values (JSONB), IP, user agent. **Insert-only at the application level, not yet at the DB privilege level** — corrected in Phase 14: this file previously pre-committed "Phase 14 hardening removes UPDATE/DELETE grants for the app role," but Phase 14's review found this deployment has no separate, lower-privileged "app role" to revoke anything from (`DATABASE_URL` connects as the same Supabase project-owner-equivalent role every migration runs as). The concrete fix — a genuinely separate runtime role — is documented in DEPLOYMENT.md's "Database Privileges" section, not executed, since it means rotating live credentials the running application depends on. See PROJECT_STATUS.md's Phase 14 Known Issues and Next Actions.
- **`clinical_access_log`** — read audit for sensitive records (chart views, encounter views, result views). Gated behind a separate `audit.review` permission held only by Org Admin/compliance — most roles, including the clinician being logged, cannot browse it. Insert-only at the application level, same caveat as above. **Had zero callers from Phase 1 through Phase 13** despite the write path existing since Phase 1 — wired up for real in Phase 14, called from `getEncounter()`, `listPatientLabResults()`, and `listPatientImagingResults()` (the "chart/encounter/result views" this bullet names). Not yet wired into every clinical read path — see PROJECT_STATUS.md's Phase 14 Known Issues for exactly what is and isn't covered.

## 6. Other Controls (spec.md §75)

- Validation: Zod at every input boundary (API route, server action, form).
- Injection: Prisma parameterized queries only; raw SQL is a reviewed exception, never default.
- XSS: React's default escaping; any rich-text clinical note field gets explicit sanitization on both write and render.
- CSRF: `SameSite` cookies + double-submit token for any non-Server-Action state-changing route.
- Rate limiting: auth endpoints and public booking endpoints (Phase 12).
- File upload: MIME allow-list validated by content-sniffing (not extension), size caps, image re-encode to strip EXIF, storage outside the web root, served only via signed URLs (Phase 2 documents, Phase 7 employee docs).
- Secrets: environment variables only, validated present at process boot, never committed (`.env` gitignored from commit 1).
