# 3. PATIENT 360 DESIGN PRINCIPLE

Patient 360 should answer five questions quickly:

1. Who is this patient?
2. Is there anything important I need to know immediately?
3. What is happening with this patient now?
4. What happened recently?
5. What should I do next?

The page should not require staff to inspect multiple tabs merely to answer these basic questions.

# 28. PATIENT 360 PERFORMANCE — IMPORTANT

P2's measured performance baseline identified Patient 360 as the heaviest screen by query count:

approximately **25 database round trips**.

It was a fan-out of many small correctly-scoped queries, not a major N+1.

P3.2 must NOT make this worse unnecessarily.

Before adding queries:

Inspect how Patient 360 loads tab data.

Determine which data is:

* required immediately for header/overview
* required only after opening a tab

Where reasonable, avoid eagerly loading heavy datasets solely for inactive tabs.

Possible approaches include existing Next.js server-component/navigation patterns, separate tab routes/search params, lazy client/server fetch, or another architecture-consistent mechanism.

Do NOT introduce Redis.

Do NOT introduce a caching system.

Do NOT create a new API layer just for this.

Do NOT perform speculative optimization.

The objective is:

> Improve Patient 360 UX without increasing unnecessary database fan-out.

If practical, measure query count before and after using the same methodology as `PERFORMANCE_BASELINE.md`.

Report real numbers only.

Do not fabricate timings.
