# Performance & Concurrency Capacity — P4.5

Evidence-based capacity findings for Avant HIS, produced by the P4.5 load-testing
phase. This document is the durable reference; the full narrative (including every
scenario's numbers, root-cause reasoning, and the acceptance decision) is in
[`P4_5_PERFORMANCE_CONCURRENCY_LOAD_VALIDATION_REPORT.md`](../P4_5_PERFORMANCE_CONCURRENCY_LOAD_VALIDATION_REPORT.md).

**Re-running this validation**: see [`load-tests/README.md`](../load-tests/README.md)
for exact commands. Every script here is committed and reproducible against a
dedicated, disposable `his_load_test` database — never `his_dev`/`his_test`/remote
Supabase.

## 1. Test Environment

- **Host**: single developer sandbox — 4 logical CPUs, Docker allocated ~4 CPU /
  8GB RAM. Postgres 17 (Docker), the Next.js server-under-test (`next start`
  production build), and the Node.js load-generator client **all shared these
  same 4 cores simultaneously** during every test in this document. This is a
  material, honestly-disclosed confound — see §12 "Known Limits".
- **Database**: `his_load_test`, a dedicated PostgreSQL database created and
  migrated by `scripts/db/load-test-setup.ts`, fully isolated from `his_dev` /
  `his_test` / any remote database. Guarded by `assertIsLoadTestDatabase` (same
  fail-closed pattern as `assertIsTestDatabase`).
- **App server**: a real `next build` + `next start` production build (not `next
  dev`), pointed at `his_load_test` via `DATABASE_URL`/`DIRECT_DATABASE_URL`,
  listening on port 3105.
- **Load tool**: k6 could not be installed in this environment (Chocolatey
  requires elevation + an interactive prompt this session cannot satisfy —
  confirmed no binary was produced). Per the spec's own fallback allowance, a
  narrowly-scoped custom Node.js HTTP harness (`load-tests/lib/http-client.ts`,
  ~120 lines) was built instead: a bounded worker-pool concurrent requester with
  p50/p90/p95/p99/max/RPS/error-rate computation. Read-path scenarios drive real
  HTTP GETs against real page routes; write-path scenarios call the real domain
  functions directly (Node-level), because Next.js Server Actions use a
  build-specific hashed action-reference encoding that a generic HTTP tool cannot
  target without reverse-engineering that build's own output — this mirrors the
  codebase's own existing `test/integration/*-concurrency.test.ts` pattern and
  exercises the identical transactions/locks/constraints against the identical
  database.

## 2. Load Model

- **Data volume**: 10,000 patients, 20,000 appointments, 9,648 encounters, 3,000
  clinical orders, 10,000 invoices / 20,056 charges+invoice-lines / 8,406
  payments+allocations, 18,406 journals / 36,812 balanced journal lines
  (verified `SUM(debit)=SUM(credit)=7,339,934.99`), 3,000 login-history rows,
  5,000 synthetic outbox-history rows (98% completed / ~1.5% failed / ~0.5%
  dead-letter — a deliberately realistic historical distribution, not a defect;
  see §8). 3 branches, 30 providers, 150 products (370 batches), 250 staff users
  across 11 roles.
- **Sessions**: 265 real `Session` DB rows (same `hashToken` mechanism as
  production), provisioned across all 11 roles by
  `load-tests/lib/provision-sessions.ts`.
- **Scenarios**: 11 named read-path HTTP scenarios (Reception, Nursing, Doctor,
  Lab, Radiology, Pharmacy, POS, Inventory, Accounting, HR, Dashboard) and 4
  write-path concurrency scenarios (Stock, Invoice, Payment, Refund), all under
  `load-tests/`.

## 3. Performance Targets

No pre-existing SLA was defined for this system. This phase establishes the
first evidence-based numbers rather than testing against a prior target; see
§9 "Production Capacity Recommendation" for what is now recommended going
forward.

## 4. Data Volume

See §2 above — all counts are real rows in `his_load_test`, generated by

everything else, not with a Patient-360-specific defect.

**Lab / Radiology were the two worst-performing scenarios by a wide margin.**
Investigated in depth — see §11 "Query Profiling".

## 6. Connection Pool

`src/lib/db.ts` was made configurable via `DB_POOL_MAX` (default remains 3,
production-unchanged) specifically so this comparison could be run without
hand-editing the file (see `src/lib/db.ts`'s own comment, referencing this
section).

| Pool max | Scenario | RPS | p50 | p95 |
|---|---|---:|---:|---:|
| 3 (default) | reception@50 | 8.6 | 5413ms | 8055ms |
| 5 | reception@50 | 5.0 | 9683ms | 13955ms |
| 3 (default) | lab@50 | 2.1 | 21063ms | 42456ms |
| 5 | lab@50 | 2.2 | 20065ms | 36075ms |

Pool=5 did **not** outperform pool=3 — reception was measurably worse; lab was a
wash. This is a real, counter-intuitive result, and it was re-run (cold and
warm) to rule out a one-off. `pg_stat_activity` during a separate 150-concurrency
burst (see §7) directly confirmed: **Postgres connections sat mostly idle even
under 150-way concurrent HTTP load** — the app's pool never saturated. That
evidence positively **rules out** two candidate explanations: observed lock
contention (zero waiting locks at every sample, §7) and local connection-pool
saturation (idle connections throughout). Targeted backlog closure, item 12C:
what it does NOT do is positively prove which remaining factor IS the cause —
CPU/event-loop scheduling in the shared 4-core sandbox (Postgres container +
app server + load-generator client all contending for the same cores) was not
independently instrumented (no CPU-utilization or event-loop-lag metric was
captured during these runs). **Shared compute/CPU scheduling is the leading
explanation in this environment, not a conclusively isolated root cause** —
it is the only candidate evidence doesn't rule out, and it is consistent with
every observation made, but it was not directly measured the way lock
contention and pool saturation were.

**Recommendation: keep the production default at `max: 3` unchanged.** No local
evidence justifies raising it, and this environment cannot cleanly separate
"pool size" from "shared-CPU confound" to prove a higher value would help even
if the confound were absent. A real, separately-resourced production/staging
host (§10) is required before any pool increase is justified — raising it
without that evidence risks a shared connection-pooler's cap (see `src/lib/db.ts`'s
own existing Supabase-pooler comment) for no proven benefit.

## 7. Transaction / Lock Findings

`pg_stat_activity` and `pg_locks` were polled every 2s (8 samples, 16s window)
during a sudden 150-concurrency POS burst (see §13 "Spike Test"):

```
[t=0s]  total_conns=1  waiting_locks=0
[t=2s]  total_conns=4  waiting_locks=0   (idle, wait_event_type=Client) x3
[t=4s..14s] total_conns=4  waiting_locks=0   (unchanged for the rest of the burst)
```

**Zero waiting locks at any sample, for the entire burst.** Total connections
never exceeded 4 (3 app-pool connections + 1 poller connection) — confirming
the pool=3 cap held exactly as configured, and confirming those 3 connections
were frequently *idle* (not busy) even while 150 concurrent HTTP requests were
in flight server-side. No lock contention or deadlock was observed in any test
run in this phase. This positively rules out DB-lock-bound and DB-connection-
bound explanations for the local ceiling (§6); it does not, on its own,
positively prove a compute/CPU-bound cause — see item 12C's wording in §6.

## 8. Outbox Performance

Every write-path scenario (Stock, Invoice, Payment, Refund) dispatches its
Outbox event **inline** (the codebase's existing P4.4 dispatch model — no
background worker). Live (non-seed) outbox events created during this phase's
scenario runs:

```
completed=34, failed=0, dead_letter=0, pending=0, processing=0
```

**Zero backlog, zero failures, zero stuck-processing rows** across every write
scenario run, including under 25-way concurrent `generateInvoice`/`recordPayment`
calls. The 5,000 pre-existing "failed=78, dead_letter=25" rows visible in a
raw status count are **synthetic seed history** (`payload.loadTestSeed: true`,
`lastError: "Load-test seed synthetic failure"`), deliberately injected by
`generate-load-data.ts` for a realistic operations-dashboard starting point —
not real failures from this phase's load testing. Targeted backlog closure,
item 12G: stated explicitly — this deliberately-seeded synthetic history
makes `his_load_test`'s own Outbox operational-health snapshot
**non-production-like on purpose** (a real, freshly-deployed production
Outbox would not start with a 1.5%/0.5% failed/dead-letter baseline). Anyone
reading `his_load_test`'s own operations dashboard or a raw status count
directly must not interpret those 103 synthetic rows as evidence of a real
dispatch-health problem — the only real signal for this phase's own load
testing is the "live (non-seed) outbox events" count above. See §5's write-up
in the full report for the inline-dispatch latency cost measurement
(uncontended `generateInvoice`=861ms, `recordPayment`=342ms,
`recordAdjustment`=330ms — all inclusive of their full inline dispatch chain).

## 9. Capacity Findings

**Capacity curve (POS scenario, representative — chosen because reads +
writes both route through it in production):**

> **Targeted backlog closure, item 12B — read vs. write capacity.** The
> 25→200 concurrency curve below is an **HTTP read/navigation workload**
> (`GET /pos`, `/invoices`, `/invoices/[id]`) — it does **not** include
> `generateInvoice`/`recordPayment` writes. Write-path concurrency
> (invoice/payment/refund/stock) was validated **separately**, through real
> domain-function calls, at concurrency up to 25 (§7 of the full report) —
> not through this HTTP curve, and not up to 200. Do not read "the system
> handled 200 concurrent POS requests" as "the system handled 200 concurrent
> invoice/payment writes" — those are two different, separately-measured
> claims in this document.

| Concurrency | RPS | p50 | p95 | Error % | Classification |
|---:|---:|---:|---:|---:|---|
| 25 | 11.8 | 2222ms | 2454ms | 0.00% | Acceptable / Mildly Degraded |
| 50 | 11.5 | 4451ms | 4816ms | 0.00% | Degraded |
| 100 | 8.4 | 11354ms | 14996ms | 0.00% | Severely Degraded (RPS falling, latency 5x) |
| 150 | 8.7-9.6 | 15421-17689ms | 18015-19908ms | 0.00% | Severely Degraded |
| 200 | 10.2 | 19885ms | 21017ms | 0.00% | Unsustainable for normal interactive use |

Targeted backlog closure, item 12A: the classification above was revised from
an earlier draft that called concurrency 25/50 "Healthy" — a p95 around
2.5-4.8s is not healthy by any interactive-usability standard, even though
nothing broke and no data was corrupted. **Correctness/stability and
interactive usability/performance are separate axes, deliberately not
conflated here**: every row's Error % column is 0.00% (a real, verified
correctness/stability fact — see §14-17's write-path proofs and §9's error
count), which is genuinely good news; but a multi-second p95 at even the
lightest tested concurrency (25) means the *interactive experience* was
already degraded in this environment well before any failure occurred. Read
"0.00% errors" as "nothing crashed or corrupted," never as "this was fast."

**No request ever failed at any concurrency level tested, up to 200, in the
read/navigation HTTP scenarios** (see item 12B/F below for what that
statement does and doesn't cover). The system degrades gracefully (rising
latency, flat-to-falling RPS) rather than failing outright in this
environment — a materially different (and better) finding than an
error-rate collapse would be, but it does mean this sandbox's compute
ceiling was reached, and interactive usability was already poor, well
before any correctness or stability boundary was.

## 10. Production Capacity Recommendation

**This local validation does NOT establish a production concurrency number.**
Per the phase's own mandatory honesty requirement: this is *local architectural
and concurrency-correctness validation*, not a cloud capacity benchmark. The
observed ceiling (RPS plateauing ~8-12, latency climbing steeply past
concurrency 50-100) is a property of this **single 4-core sandbox**, where the
database, application server, and load-generator client all compete for the
same cores — not a property necessarily shared by a properly-resourced,
separately-provisioned production host.

**What this phase does support:**
- Zero correctness failures in the separately-executed, real-domain-function
  write-path concurrency scenarios (stock/invoice/payment/refund invariants,
  §14-17), tested up to concurrency 25.
- Targeted backlog closure, item 12F: **zero HTTP errors in the tested
  read/navigation scenarios up to concurrency 200, and no correctness
  failures in separately executed contended write scenarios** — not "every
  operation was exercised identically over HTTP up to 200," which this
  phase never claims. See item 12B above for the same read/write
  distinction applied to the capacity curve specifically.
- The connection pool default (`max: 3`) is not shown to be a bottleneck in
  this environment and should not be raised without new evidence from a
  separately-resourced staging/production host.
- No lock contention or deadlock was observed under sustained concurrent load.

**What this phase does NOT support, and must not be claimed:** "supports 200
concurrent users in production." **A staging or production-equivalent cloud
load test remains a deployment requirement** before any concurrency claim is
made to a customer or used in a go-live decision. See §13.

## 11. Query Profiling

The two worst-performing scenarios (Lab p50 9645-21063ms, Radiology p50
6341-12415ms) were investigated directly.

**Root-cause finding**: it is **not the query**. Direct Prisma-level timing of
`listLabQueue`'s underlying query (478 realistic rows, 5 joined relations)
measured 76-267ms warm — nowhere near the multi-second page latencies observed
under load. An isolated concurrency=1 (no-contention) HTTP request to
`/laboratory` measured **p50=326ms** — closely matching the raw query cost.
This proves the multi-second latencies at concurrency 25-50 are almost
entirely **concurrency/queueing cost** (the same shared-CPU-sandbox ceiling
documented in §6), not an intrinsically slow endpoint.

**Fix made at the time of P4.5 (superseded — see below):** both `listLabQueue`
and `listRadiologyQueue` had **no `take` limit at all** — an unbounded
`findMany` that grows linearly with order volume forever. P4.5 initially
added a bare `take: 200` safety cap as a narrow, forward-looking fix, with
an inline comment explaining it was a safety bound, not a fix for the
measured latency. Its own "before/after" table at the time compared 478
unbounded rows against a *hypothetical* `take:50` query timing (69-120ms),
never an actual `take:200` measurement — flagged and corrected below (item
12D) rather than left as a claim that was never directly measured.

**Superseded by the targeted commercial/safety backlog closure (real
pagination, not a cap):** a bare row-count cap on a clinical operational
queue silently hides order 201+ with no way to reach it, which was judged
unacceptable for a production clinical workflow. `listLabQueue` and
`listRadiologyQueue` now take `page`/`pageSize` and return
`{orders, total, page, pageSize, totalPages}` — the same
`resolvePage`/`paginationSkipTake`/`totalPages` convention every other
paginated list in this codebase uses — with `PaginationControls` on both
pages. No record is unreachable regardless of how large the queue grows. See
`TARGETED_COMMERCIAL_SAFETY_BACKLOG_CLOSURE_REPORT.md` (item 2) for the full
before/after evidence of this replacement.

| | Before (P4.5, unbounded) | After (real pagination) |
|---|---:|---:|
| Rows returned | 478 (unbounded) | ≤50 per page (default page size), any page reachable |
| Query time (warm) | 76-267ms | 69-120ms (a `take:50` page-1 query is representative of every page's cost — confirmed directly, not inferred, by the targeted-closure batch) |

No other query in this phase's testing showed evidence of needing an index or
N+1 fix — Patient 360, the Management Dashboard, and the Reports page all
performed in line with their pre-existing documented shape
(`PERFORMANCE_BASELINE.md`), scaling only with the same general concurrency
ceiling as everything else.

## 12. Known Limits

- **Single 4-core shared sandbox** — Postgres, the app server, and the load
  client all contend for the same cores. This confounds the pool-size
  experiment (§6) and inflates every scenario's absolute latency numbers under
  concurrency. A staging/cloud test on separately-provisioned infrastructure is
  required to get numbers that reflect real production capacity.
- **Soak test reduced from spec's 60-90min target** to a shorter window (see
  the full report's Soak Test section for the exact duration run and why) —
  session time budget, not a technical blocker. Targeted backlog closure,
  item 12E: **stated plainly, this short run validates short-duration
  steady-state behavior only.** It does NOT prove long-duration memory
  stability, the absence of a slow leak, or genuine 60-90 minute endurance —
  none of those can be concluded from a 6-minute window, and this document
  does not claim them. A proper staging soak at the spec's original duration
  remains a required step before any endurance claim is made (see §13). The
  mechanism (`load-tests/soak/soak-test.ts`) is unchanged and can be re-run
  for longer: `npx tsx load-tests/soak/soak-test.ts <minutes> <concurrency>`.
- **k6 unavailable** in this environment (see §1) — a custom harness was used
  instead. It faithfully measures real HTTP latency/RPS/error-rate but lacks
  k6's richer protocol/scripting features; this was judged sufficient for
  this phase's scope.
- **No staging/cloud environment exists in this session** — the staging load
  test the spec calls for is recorded as a deployment requirement (§10), not
  performed here.

## 13. Staging Validation Requirement

**Before any customer-facing capacity claim ("supports N concurrent users") is
made, a staging or production-equivalent cloud load test must be run** against
infrastructure matching the intended deployment (real Vercel function
instances or equivalent, a real managed Postgres instance/pooler, realistic
network latency between them) using the same committed `load-tests/` scripts.
No staging environment exists for this engagement at the time of this report —
this is recorded as a required step before go-live, not performed here.
