# 1. PURPOSE

P3.11 is:

# NOTIFICATIONS / TASKS / OPERATIONAL AWARENESS

This is NOT a whole-system audit.

The objective is:

> Give staff a reliable, role-aware way to know what requires their attention across existing HIS workflows without requiring them to manually inspect every module.

Conceptually:

Operational Event
→ Notification / Operational Signal
→ Relevant User / Role
→ Notification Center
→ Destination Workflow
→ Read / Resolved State

The HIS should help answer:

> "What needs my attention right now?"

Do NOT build another event engine.

Do NOT rebuild the existing outbox.

Do NOT build Slack/Teams/email-style collaboration.

# 3. DISTINGUISH THREE CONCEPTS

Do not mix these together.

## A. User Notification

Something a staff member should know.

Examples:

* leave approved
* appointment conflict
* result ready
* stock issue

## B. Operational Work Queue

Existing module-specific work requiring action.

Examples:

* Lab ordered tests
* Pharmacy outstanding prescriptions
* Cashier unbilled Charges
* HR pending leave requests

These already belong primarily to their modules.

## C. System / Integration Exception

Something technically failed.

Examples:

* accounting event failed
* outbox dead-letter

These belong to Admin/Finance exception workflows.

P3.11 may surface awareness of these items, but must NOT duplicate their operational source of truth.

# 11. READ OWNERSHIP

Server-side enforcement is mandatory.

Never trust notification IDs supplied by the client.

notification.userId / recipient
→ session.user.id

and organization boundaries as appropriate.

* exception
* assignment
* completion requiring follow-up
* approval

# 41. DUPLICATE NOTIFICATIONS

# 42. CONCURRENCY

* same event handled twice
* mark same notification read twice
* mark-all-read concurrent with new notification creation

Do not build unnecessary locking.
