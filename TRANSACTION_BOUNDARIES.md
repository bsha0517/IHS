# Transaction Boundaries

P1 §32's own instruction: document, for each of the ten named multi-step operations, what a single "atomic business action" actually consists of, and how this codebase makes it atomic — a database transaction, an outbox event, a claim-before-act guard, or (where already true) nothing further needed. Written during the P1 remediation pass's Batch 8 (2026-08-27); each boundary below was verified by reading the current implementation, not inferred from naming. Where a boundary was found missing or incomplete, the fix landed in this same batch — see P1_FINANCIAL_INTEGRITY_FINDINGS.md for the originally-catalogued finding IDs (A1-A9, B1-B11) this table closes out, and ARCHITECTURE.md's per-workflow sections for the fuller design narrative.

**Convention used throughout this pass**: a Prisma `$transaction` is the atomicity boundary for everything that must commit-or-rollback together *right now* (the state change itself, plus any row it directly depends on). A `writeOutboxEvent` call *inside that same transaction*, dispatched immediately after via `dispatchPendingOutboxEvents`, is the boundary for anything that's logically part of the same business action but crosses into a different domain (accounting postings, cross-domain notifications) — see ARCHITECTURE.md §15. This is deliberate, not a workaround: an accounting posting failing (e.g. an unconfigured account mapping) must never roll back the clinical/operational fact that already happened, but it also must never be silently lost — the outbox's own retry/dead-letter machinery (P0-02) is what makes "queue it, don't inline it" safe.

| # | Operation | Function(s) | Boundary |
|---|---|---|---|
| 1 | Invoice issuance | `generateInvoice` (billing/invoices.ts) | One `$transaction`: atomically claims every selected charge (`pending` → `invoiced`, `updateMany` with a status precondition — **fixed this batch, finding A5**, previously an unconditional per-charge update with no re-check), creates the Invoice + InvoiceLines, writes `InvoiceIssued` to the outbox. `postInvoiceIssued` (the journal posting) and commission accrual both run async off that event. |
| 2 | Payment posting | `recordPayment` (billing/payments.ts) | One `$transaction`: `applyPaymentAtomically` (single atomic `UPDATE ... WHERE paid_amount + amount <= total_amount`, P1 §29, fixed in Batch 2) guards against two concurrent payments overpaying; a fresh `IdempotencyKey` claim (**new this batch, §33**) guards against the *same* tender being double-submitted (a double-click within the balance headroom, which the overpayment guard alone doesn't catch); then one Payment + PaymentAllocation row per tender, then `PaymentReceived` to the outbox. `postPaymentReceived` and commission accrual run async. |
| 3 | Refund | `requestRefund` → `authorizeRefund` → `completeRefund` (billing/refunds.ts) | Three distinct steps, three distinct permissions (segregation of duties) — only `completeRefund` moves money, so only it needs the heavy guard: one `$transaction` that atomically claims the refund itself (`authorized` → `completed`, `updateMany`, P1 §7/Batch 2) *before* `applyRefundAtomically`'s own atomic balance guard, then writes `RefundCompleted` to the outbox. `postRefundCompleted` and commission clawback (`reverseCommissionsForRefund`, §19) run async. |
| 4 | Package consumption | `consumeSession` (packages/service.ts) | One `$transaction`: `SELECT ... FOR UPDATE` locks the PatientPackage row (**fixed in Batch 7, finding A6** — was an unlocked check-then-act race), re-validates status/expiry/remaining-count under that lock, then a fresh `IdempotencyKey` claim (**new this batch, §33**) on top guards the double-click case the lock alone doesn't (burning two sessions from ample headroom, not just overselling the last one) — then the PatientPackageSession insert, the exhausted-flip, and `PackageSessionConsumed` to the outbox, all in the same transaction. |
| 5 | Dispensing | `dispenseRecord` / `returnDispensingRecord` (pharmacy/dispensing.ts) | One `$transaction` each. `dispenseRecord`: claims the record (`verified` → `dispensed`, `updateMany`, P1 §14, fixed in Batch 4) *before* `consumeStock` + `generateSystemCharge` + the medication-history upsert + the `ProductSold` outbox write — a double-click can't double-deduct stock or double-bill. `returnDispensingRecord`: `SELECT ... FOR UPDATE` locks the parent DispensingRecord before re-validating the over-return guard against a fresh aggregate read, since `quantityReturned` is a derived sum with no single column to atomically increment. |
| 6 | Inventory consumption | `consumeStock` (inventory/stock.ts) | Runs inside whatever transaction the caller (dispensing, POS product sale) already opened. `SELECT ... FOR UPDATE` on every `ProductBatch` row for the product (**fixed this batch, finding A8** — previously an unlocked `SUM` read with no lock at all) serializes concurrent consumers of the same product before FEFO allocation runs, so two near-simultaneous low-stock consumptions can't both read the same pre-consumption balance and together oversell it. |
| 7 | Goods receipt | `createGoodsReceipt` (procurement/goods-receipts.ts) | One `$transaction` (already correctly atomic before this batch — the receipt, every line, `receiveStock`'s batch+ledger inserts, the PO status recompute, and the `GoodsReceiptCompleted` outbox write all commit or roll back together). The gap was idempotency, not atomicity: **fixed this batch, finding B8** — an `IdempotencyKey` claim as the transaction's first statement means a double-submitted request (double-click, network retry) replays the original receipt instead of creating a second full physical-receipt record with its own stock entries and posted journal. |
| 8 | Supplier invoice | `createSupplierInvoice` / `recordSupplierPayment` (procurement/supplier-invoices.ts) | `createSupplierInvoice`: one `$transaction` (SupplierInvoice create + `SupplierInvoiceCreated` outbox write) — already correct since Batch 4 (finding B6). `recordSupplierPayment`: one `$transaction`, now opening with `applySupplierPaymentAtomically` (**fixed this batch, finding A3** — the AP-side mirror of `applyPaymentAtomically`, previously an unlocked read-then-write exactly like the pre-Batch-2 patient-payment race) before the SupplierPayment create and `SupplierPaymentRecorded` outbox write. |
| 9 | Payroll approval | `approvePayrollRun` (payroll/payroll.ts) | **Fixed this batch, finding B10.** Previously two separate, unprotected steps: `db.payrollRun.update(...)` committed on its own, then `postPayrollApproved()` ran as a direct, un-transacted call — if it threw (most plausibly a missing account mapping), the run was already stuck `"approved"` with no journal and no retry path short of a manual journal entry. Now one `$transaction`: an `updateMany` claim (`draft`/`review` → `approved`, guarding against double-approval too) plus a `PayrollApproved` outbox write, committed together; `postPayrollApproved` runs async off that event, so a posting failure now lands in the P0-02 retry/dead-letter machinery like every other posting trigger. |
| 10 | Payroll payment | `markPayrollPaid` (payroll/payroll.ts) | **Fixed this batch, finding B10 (second half).** Same shape as #9: one `$transaction` — an `updateMany` claim (`approved` → `paid`), the commission-accrual `paid` flip, and a `PayrollPaid` outbox write, all together; `postPayrollPaid` runs async. |

## Deliberately not given the `IdempotencyKey` treatment

Not every "create a new record" action in this codebase needed it — only where a double-click/retry would produce a real duplicate *side effect* (money moved, stock consumed, a session burned). Two were reviewed and found not to need it:

- **`bookAppointment`** — a double-booked identical slot for the same patient/provider is a UX annoyance (two rows on the calendar), not a financial or clinical-safety issue, and the DB's own exclusion constraint already prevents the far more important case (provider/room double-booking against *different* appointments).
- **`purchasePackage`** — creates a `PatientPackage` + a `Charge`; a genuine double-click would be caught the same way any other double-submitted charge is (visible immediately in the pending-charges list, voidable before invoicing) rather than silently compounding like a payment or a stock deduction would.

## Financial period control (P1 §31) and its relationship to this table

`postJournal` (accounting/posting-service.ts) — the single chokepoint every one of the ~17 posting functions above funnels through — now also enforces `assertPeriodOpen` (accounting/periods.ts) before writing anything, closing a month to further posting once accounting has closed it. This isn't a duplicate-prevention or atomicity mechanism like the rest of this document — it's a *when* control, not a *how* control — but it lives in the same chokepoint this table repeatedly relies on, so a reader of this file should know it's there. See ARCHITECTURE.md's Central Accounting Posting Service section and `periods.ts`'s own doc comment for the full design and its deliberately limited scope (a lock, not a full close-the-books ceremony).
