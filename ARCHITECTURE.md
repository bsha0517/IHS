# ARCHITECTURE.md

Living reference for the HIS system architecture. Updated at the end of every phase. Rationale/tradeoffs for decisions live in [BLUEPRINT.md](BLUEPRINT.md) and individual ADRs in `/docs/adr/`; this file is the current-state operational reference.

## 1. Style

Modular monolith. One Next.js (App Router, TypeScript) application, one PostgreSQL database. Domains are isolated by folder/module boundary and service-layer contracts, not by network boundary. See BLUEPRINT.md §74/§2 for rationale.

## 3. Patient Journey (canonical spine)

```
Registration → Duplicate Check → Appointment → Arrival → Check-In → Queue
 → Encounter (± Episode) → Vitals → Consultation → Diagnosis → Orders → Prescription
 → Encounter Finalized → Charges Captured → Invoice → Payment → Accounting Journal
 → Commission Accrual → Patient Timeline → Follow-Up
```

Order branches: `Encounter → Lab Order → LIS → Result → EMR`; `Encounter → Medication Order → Pharmacy → Dispensing → Inventory → EMR`; `Encounter → Imaging Order → RIS → Report → EMR`; `Encounter → Procedure → Room + Inventory → Charge`.

**P1 Batch 6 — Patient ACTIVE/INACTIVE/DECEASED (§24):** `Patient.status` (the enum already existed) had no function anywhere that could change it — P0 made `Patient`'s FKs `Restrict`, so a patient who stops attending, or who has died, previously had no explicit lifecycle action at all. `updatePatientStatus` closes this: ACTIVE↔INACTIVE freely reversible either direction, DECEASED reachable from either but terminal through this function (undoing it is deliberately not a self-service action — the same gravity `markEncounterEnteredInError`'s own terminal reasoning applies). Every call requires a reason; user/timestamp come from the audit log, same convention as `Invoice.voidReason`.

**P1 Batch 7 — appointment reschedule as a real workflow, centralized status transitions (§26/§27):** `rescheduleAppointment` already created a genuinely new `Appointment` row (`rescheduledFromId` link, original marked `rescheduled` rather than overwritten) and already relied on the DB's own `appointment_provider_no_overlap`/`appointment_room_no_overlap` exclusion constraints to reject a conflicting new slot — both correct and unchanged. Two real gaps closed: the reason for rescheduling was never actually captured (the original's status-history row hardcoded `"Rebooked as APT-..."`, discarding whatever the staff member's real reason was) — `rescheduleAppointmentSchema` now requires one, stored alongside the mechanical note; and **the function existed with zero UI ever calling it** — `RescheduleDialog` (`appointments/reschedule-dialog.tsx`) is the first surface that actually lets a user trigger it. Every appointment status change (`confirmAppointment`, `markArrived`, `checkIn`, `callPatient`, `completeConsultation`, `cancelAppointment`, `markNoShow`, `rescheduleAppointment`) now validates through one shared `APPOINTMENT_TRANSITIONS` map (`appointments/service.ts`, using Batch 6's `assertValidTransition`) instead of each function's own inline `allowedFrom` array — `AppointmentStatusHistory` (already existed) is unchanged as the system of record.

**P1 Batch 7 — package session consumption locked, Refund gets a number (§28/§30):** `consumeSession` (packages/service.ts) had the exact unlocked check-then-act race P1_FINANCIAL_INTEGRITY_FINDINGS.md's A6 named — two simultaneous completions against a package with one session remaining could both pass validation and both insert. Fixed with a `SELECT ... FOR UPDATE` lock on the `PatientPackage` row, re-validating status/expiry/remaining-count against a fresh read taken under that lock, before the insert — the same discipline Batch 6's `approveLeave` established for `LeaveBalance`. Separately, `Refund` — alone among Invoice/Payment/GoodsReceipt/SupplierInvoice — had no human-readable number at all; `refundNumber` (nullable — assigned only at `completeRefund`, the first point a refund is guaranteed to actually move money, mirroring how a Payment's own `receiptNumber` is only ever real once tendered) closes it via a new `"RFD"` sequence type.

**P1 Batch 8 — basic financial period control (§31):** a new `AccountingPeriod` model (`accounting/periods.ts`) exists only as rows for calendar months that have actually been *closed* — an unclosed month is implicitly open, nothing pre-created. `assertPeriodOpen` is called from inside `postJournal` itself — the single chokepoint every one of the ~17 posting functions in this file funnels through — so this one guard blocks posting into a closed month for every caller at once, including manual journal entries (the one path where a user picks an arbitrary `journalDate`; every system-generated posting always dates itself `new Date()`, necessarily in whatever month is currently open). No override permission exists: closed means closed for everyone, including accountants — the only way past it is `reopenPeriod` (audited, same convention as `Patient.status`/`Encounter.status`: the row's presence plus the audit trail *is* the open→closed→reopened history, no separate history table). Deliberately does not build a full close-the-books ceremony (closing entries, a reconciliation checklist, period-end snapshots) — P1 §31's own instruction was to document that as a separate, larger effort rather than rush a partial version; see PROJECT_STATUS.md's Next Actions.

**P1 Batch 8 — transaction boundary review and idempotency review (§32/§33):** a systematic pass over the ten operations P1 §32 names, documented in full in the new [TRANSACTION_BOUNDARIES.md](TRANSACTION_BOUNDARIES.md). Three were already correctly atomic and needed nothing (Refund completion, Dispensing, Goods Receipt's own transaction shape). Five had real gaps, all closed this batch: **finding A5** (`generateInvoice` flipped charges `pending`→`invoiced` with an unconditional per-charge update, no re-check — two concurrent invoice-generation calls selecting the same charge could both succeed and double-bill it; fixed with an atomic bulk `updateMany` claim, same "claim before acting" shape as `dispenseRecord`); **finding A8** (`consumeStock`, inventory/stock.ts, had zero concurrency protection at all — an unlocked `SUM` read before FEFO allocation meant two concurrent low-stock consumptions could both read the same balance and together oversell it; fixed with a `SELECT ... FOR UPDATE` lock on the product's `ProductBatch` rows before the balance read); **finding A3** (`recordSupplierPayment` had the exact pre-Batch-2 patient-payment race — unlocked read-then-write on `paid_amount` — fixed with `applySupplierPaymentAtomically`, the AP-side mirror of `applyPaymentAtomically`); **finding B8** (`createGoodsReceipt` had zero duplicate-submission protection — every call unconditionally created a new receipt, stock entries, and a posted journal; fixed with a new shared `IdempotencyKey` primitive, `platform/idempotency.ts`); and **finding B10** (payroll's `approvePayrollRun`/`markPayrollPaid` updated status and posted the journal as two separate, unprotected steps — a posting failure left the run stuck with no journal and no retry path — flagged real in Batch 5 and deliberately left open until this batch; now one transaction each, writing the status change and a `PayrollApproved`/`PayrollPaid` outbox event together, with an `updateMany` claim guarding against double-approval/double-payment too). The same new `IdempotencyKey` primitive also closes two gaps §33 named that weren't in P1_FINANCIAL_INTEGRITY_FINDINGS.md's original catalogue: `recordPayment` (the existing `applyPaymentAtomically` guard prevents *overpayment* from two different concurrent payments, but does nothing for the *same* tender double-submitted within the balance's headroom) and `consumeSession` (Batch 7's row lock prevents overselling the *last* session, but not double-consuming from ample headroom). `IdempotencyKey` is deliberately a shared table + primitive (`claimIdempotencyKey`/`recordIdempotentResult`/`resolveDuplicateRequest`, keyed by `(organizationId, scope, key)`) rather than a bespoke nullable+unique column bolted onto each affected model — the same "one shared chokepoint, many call sites" taste as `assertValidTransition` (Batch 6) and `nextNumber()` (Batch 7).

**P1 Batch 9 — the full adversarial test list (§34):** twelve real-failure-condition tests P1.md names by name. Ten already had real regression coverage from earlier batches — `test/integration/adversarial-conditions.test.ts` is the new single index proving all twelve exist and documenting exactly which file covers each, plus the two genuinely missing ones: concurrent appointment booking (two simultaneous `bookAppointment` calls for the same provider's overlapping slot — proves the DB's own exclusion constraint, not an app-level check, is what actually serializes it) and finalized clinical-record modification (`saveNote`/`enterNumericResult` both correctly refuse to edit a finalized ClinicalNote or a verified LabOrderTest line in place — `createAmendment` is the only real path past the former, re-entering the enter/verify cycle isn't possible for the latter by the transition map's own design).

**P1 Batch 9 — report consistency and patient statement reconciliation (§35/§36):** proved, against one real transaction chain (PurchaseOrder → GoodsReceipt → SupplierInvoice → POS sale → Invoice → Payment → Refund → SupplierPayment touching Inventory/COGS/AR/AP/Revenue/Cash all at once), that every report P1 §35 names reconciles — `test/integration/report-reconciliation.test.ts` measures each figure as a before/after delta (never an absolute value, since this is a shared dev database with other data already in every account) and confirms Inventory Valuation moves by the exact COGS amount posted (P1's own literal example), AR/AP sub-ledger figures (`getFinancialReport`) move identically to their GL account balances (`trialBalance`), and Trial Balance/Balance Sheet stay internally balanced throughout. One real, already-documented divergence is asserted explicitly rather than silently glossed over: a refund's `Dr Revenue / Cr Cash` posting correctly never touches the AR account (refunding cash on an already-paid invoice isn't an AR event), while the AR *sub-ledger* figure — derived from `Invoice.paidAmount`, which a refund does decrement — rises back up by the refunded amount; see PROJECT_STATUS.md's own "Refund posting is a documented simplification" note. §36's `getPatientStatement` (new, `billing/statement.ts` — no such unified view existed before) is a chronological ledger of one patient's invoices/payments (including an insurance-tender one, labeled distinctly via `Payment.claimId`)/refunds with a running balance, proven in `test/integration/patient-statement-reconciliation.test.ts` to always land on the same outstanding figure the sub-ledger AR definition computes — by construction, since both read the identical `Invoice.totalAmount`/`paidAmount` fields, just two different ways. Surfaced as a new "Statement" tab on the patient billing view (`patients/[id]/billing-tabs.tsx`) — the minimal UI needed to expose it, per P1 §37's own "no redesign" constraint, not a new page. Writing this batch's own tests caught two real test-authoring bugs before they ever reached a shared environment, not application bugs: an unlinked `purchaseOrderId` on a test's own supplier-invoice call made it look standalone and double-recognize Inventory (the app's GR/IR logic responded exactly as designed to a genuinely malformed test input), and an early draft of the report-reconciliation test asserted an absolute value against an org-wide aggregate in a shared database rather than a before/after delta like everywhere else in the same file — both caught by the tests failing loudly rather than passing on a coincidence.

## 4. Clinical Workflow

`Episode` (optional grouping) → `Encounter` (bounded interaction, statuses `draft → active → completed → finalized`) → structured documentation (chief complaint, HPI, exam, assessment) → `Diagnosis` (ICD-coded, primary/secondary) → `CPOE Order` (lab/medication/imaging/procedure/referral/other) → `Prescription`. Finalized encounters and notes are never edited in place — corrections create an amendment row referencing the original (`amends_id`), full version chain preserved. A finalized encounter with a triggering diagnosis/procedure that is later amended does **not** retroactively alter charges already generated from it (Correction #2, approved) — a correction requires a new adjustment charge/credit.

**P1 Batch 6 — Encounter CANCELLED/ENTERED_IN_ERROR (§23/§24):** `EncounterStatus` only ever had `draft/active/completed/finalized` — no way to mark an encounter that shouldn't have existed at all, other than the impossible option of deleting it (P0 made `Encounter`'s FKs `Restrict`). Two new terminal values plus `Encounter.cancelReason`: `cancelEncounter` (draft/active only — the encounter never produced real downstream content) and `markEncounterEnteredInError` (any non-terminal status, including `completed`/`finalized` — for content that does exist but genuinely shouldn't have; deliberately does NOT cascade into the encounter's own charges/notes/orders, each of which corrects through its own domain's own void/amendment path instead). Verified this batch, not modified: `completeEncounter`/`finalizeEncounter` were already correctly one-way, status-guarded transitions with no generic "edit a finalized encounter" path anywhere in the codebase — §23's "finalized clinical records cannot be casually changed" already held for Encounter, ClinicalNote (§4's own amendment chain), Prescription (no edit function exists at all — only `cancelPrescription`), and `ImagingOrder` (`writeReport`/`verifyImagingResult` are each individually status-gated, mirroring lab's own now-centralized guard).

Referral orders (Correction #1) distinguish `referral_scope` (`internal | external`) and track a `referral_status` (`issued → acknowledged → seen → closed`) independent of the shared CPOE status enum, in `referral_order_detail`.

Follow-up is modeled explicitly via `follow_up_recommendation` (Correction #1): `encounter_id, recommended_date, reason, status(open|scheduled|dismissed)`, queried by the notification engine and reports — not inferred from a future appointment's free-text note.

## 5. Revenue Workflow

```
Billable Event (encounter completion / order completion / dispensing / procedure completion)
 → Charge (immutable, source-typed, unbilled until invoiced)
 → Invoice (aggregates pending charges, applies line/document discount + tax)
 → Payment (single or split across tenders, allocated via payment_allocation)
 → Accounting Journal (posted automatically by the central posting service)
```

**Status: Charge → Invoice → Payment fully implemented in Phase 4** (`src/lib/domains/billing/*`). The centralized billing engine (spec.md §33) is the *only* writer of `Charge`/`InvoiceLine` — the POS UI never constructs billing data directly. `EncounterCompleted` is the live trigger for the "Consultation" source; `lab` is live as of Phase 8 (fired at test-assignment time, see §9); `pharmacy` is live as of Phase 9 (fired at dispensing time, see §10); `imaging` is live as of Phase 10 (fired at service-assignment time, see §11); `procedure`/`package`/`other` sources remain POS-entered ad-hoc with no further side effect. **`product` is a genuine second trigger as of the P1 remediation pass (Batch 3, §9-§11, 2026-08-27)** — not merely POS-entered like the others, but the one ad-hoc source type that also consumes real inventory: `Charge.productId`, set only for this source, is what `insertCharge` uses to run the exact same FEFO-safe `consumeStock()` every other inventory movement in this system goes through, in the same transaction as the charge itself (§7). **Accounting Journal implemented in Phase 6** — `InvoiceIssued`/`PaymentReceived`/`RefundCompleted` now have real handlers calling the central posting service (see §6); every invoice, payment, and refund posts a balanced journal automatically.

**Insurance path implemented in Phase 11** (see §12): `Invoice` carries `payorId`/`patientCoverageId`, splitting `estimatedPatientResponsibility`/`estimatedPayorResponsibility` at issue time (from the coverage's copay) and `finalPatientResponsibility`/`finalPayorResponsibility` post-remittance (two distinct, separately-timestamped fields, never an in-place edit of the original estimate). Deliberately not added to the Phase 4 `Invoice` schema ahead of the Payor domain existing — self-pay patients worked with zero payor configuration from Phase 4 through Phase 10 (spec.md §38), and every field this phase added is nullable, so that remains true today.

Packages (Correction #3, approved) — **sale and consumption implemented in Phase 4, accounting treatment implemented in Phase 6**: a `PatientPackage` purchase creates a pending `Charge` (source `package`) through the same engine as everything else; at invoice time `postInvoiceIssued()` credits the package-sourced portion of the invoice to `unearned_revenue` (not `revenue`), and each `patient_package_session` consumption triggers `postPackageSessionConsumed()` — a `recognize_package_revenue`-style posting moving `purchasePrice / totalSessionsAllocated` from Unearned Revenue to Revenue, pro-rata per session regardless of which of the package's bundled services the session was used against. `PatientPackage` usability remains independent of payment status (see PROJECT_STATUS.md's Phase 4 Architecture Decisions) — accounting recognition and clinical usability are two separate concerns.

## 6. Accounting Workflow

All postings go through the Central Accounting Posting Service (`/lib/domains/accounting/posting-service.ts`) — no other module writes `journal_line` directly. Intent-based methods resolve GL accounts via configurable `account_mapping` rows (keyed by branch + transaction intent), never hardcoded account numbers. Every journal is balanced (`Σdebit = Σcredit`), enforced by a DB trigger, not just application code.

**Status: implemented in Phase 6** (`src/lib/domains/accounting/*`). `resolveAccountId(organizationId, branchId, intent)` resolves against the `PostingIntent` taxonomy (14 values through Phase 6, 17 as of P1 Batch 3's `cogs`/`inventory_write_off`/`inventory_adjustment_gain`, 20 as of P1 Batch 4's `goods_received_not_invoiced`/`recoverable_tax`/`fixed_asset` — see below) — branch-specific mapping wins, falls back to the org-wide default (`branchId: null`), throws a clear configuration error if neither exists. `postJournal()` is the sole `Journal`/`JournalLine` writer, generating the sequence number (`JRN-000001`, ...) and doing a fast application-level `Σdebit = Σcredit` check before the DB's `CHECK` constraint + `DEFERRABLE CONSTRAINT TRIGGER` (see DATABASE.md) enforce it authoritatively at commit. Fifteen named posting functions cover every accounting-relevant trigger: the original eight (`postInvoiceIssued`, `postPaymentReceived`, `postRefundCompleted`, `postGoodsReceiptCompleted`, `postSupplierPaymentRecorded`, `postPackageSessionConsumed`, `postExpense`, `postManualJournal`), P1 Batch 3's `postProductSaleCogs`/`postProductSaleVoided`/`postInventoryAdjustment` (§7), P1 Batch 4's `postSupplierInvoiceCreated`/`postAssetAcquired` (§7, §8), and P1 Batch 6's `postInvoiceVoided` (below). Every asynchronous one posts via the outbox pattern (§15) — a missing account mapping never blocks the triggering clinical/revenue/inventory action, it just leaves the posting `failed` for retry; `postExpense`, `postManualJournal`, and P1 Batch 4's `postAssetAcquired` post synchronously, in the same transaction as the triggering row, since all three are direct accountant/staff actions expecting immediate confirmation. Financial reports (Trial Balance, Income Statement, Balance Sheet, a simplified direct-method Cash Flow) are computed live from `journal_line` at read time — never cached.

**P1 Batch 6 — Invoice VOID reverses its own journal, Journal REVERSAL for manual entries (§24):** `voidInvoice` (billing/invoices.ts) already existed and was already correct as a status flag (blocks voiding a paid invoice, reverts consumed Charges to `pending` so they can be re-invoiced, requires a reason) — but never reversed the `Dr AR / Cr Revenue [+Unearned][+Tax]` `postInvoiceIssued` had already posted for it. Left standing, that journal would overstate Revenue/AR forever, and — worse — re-invoicing the same reverted-to-pending Charges would double-count the revenue on top of it. `postInvoiceVoided` closes this by reading back the original journal and posting an exact mirror (every line's debit/credit swapped, same discipline `postProductSaleVoided` already established), fired via a new `InvoiceVoided` outbox event so a posting failure never blocks the void itself. Separately, `reverseJournal` (accounting/journals.ts) is the first REVERSAL path for a `Journal` at all — P0 already made sure nothing can delete one; nothing could correct one either, once posted. Scoped deliberately to `referenceType: "manual"` journals only (`postManualJournal`'s own "one-off correction" category) — a domain-tied journal (Invoice, Payment, Refund, ...) reverses through that domain's own proper workflow instead (as above for Invoice), never directly here, since reversing it out from under the domain record would desync that record's own status from what the GL now shows.

**P1 Batch 4 — the pharmacy chain's missing COGS leg (§14):** `dispenseRecord` (`pharmacy/dispensing.ts`) always consumed real stock via `consumeStock`, but discarded its returned cost instead of feeding it anywhere — the dispensed medication's revenue was recognized (charge → invoice → `postInvoiceIssued`) while its cost never was, silently overstating gross margin for every pharmacy sale. Fixed by having `dispenseRecord` fire the same `ProductSold` outbox event `insertCharge` (billing/charges.ts) fires for a POS sale, reusing `postProductSaleCogs` as-is — no new posting function needed. `returnDispensingRecord` deliberately does NOT reverse this COGS (nor the original Charge — see its own doc comment): a return is a physical stock correction, not a financial undo.

**P1 Batch 4 — GR/IR clearing account (§15):** `postGoodsReceiptCompleted` no longer credits Accounts Payable directly — it credits a new "Goods Received Not Invoiced" clearing liability (`goods_received_not_invoiced` intent), since physical receipt and the legal AP obligation are two different events, often separated by days/weeks, and stock is already sellable (FEFO-allocatable) the moment it's received. The new `postSupplierInvoiceCreated` (fired from `createSupplierInvoice` via a new `SupplierInvoiceCreated` outbox event) is what finally recognizes real AP: for a PO-linked invoice it clears GR/IR (Dr Goods Received Not Invoiced); for a standalone invoice with no linked PO it debits Inventory directly (nothing was ever provisionally recognized to clear) — either way Cr Accounts Payable for `amount + taxAmount`. An optional `SupplierInvoice.taxAmount` (recoverable purchase tax, manually entered — no supplier-side tax-rule engine exists) debits a new Recoverable Tax asset account when present. `recordSupplierPayment`'s outstanding-balance check now compares against `amount + taxAmount`, matching what `postSupplierInvoiceCreated` actually credited to AP.

**P1 Batch 4 — over-receiving guard (§16):** `createGoodsReceipt` now rejects any line whose cumulative received quantity (summed across every prior `GoodsReceiptLine` against that `PurchaseOrderLine`) would exceed the PO line's ordered quantity, unless the caller passes `allowOverReceipt: true` (a receipt-level UI checkbox, not a persisted column — the existing audit-log entry for the receipt captures that it happened).

**P1 Batch 4 — fixed-asset acquisition (§17):** `createAsset` now posts synchronously (same transaction as the `Asset` row, mirroring `postExpense`'s pattern) via the new `postAssetAcquired`: Dr Fixed Assets (a new dedicated account, never ordinary Inventory or Operating Expenses), Cr whichever tender the new `Asset.paidVia` resolves to, or Cr Accounts Payable if `paidVia` is null (acquired on credit). A cost-less asset (donated/pre-owned, tracking only) posts nothing. `Asset` also gained four nullable depreciation-readiness fields (`depreciationMethod`, `usefulLifeMonths`, `salvageValue`, `depreciationStartDate`) — schema only, no calculation or posting logic reads them yet (the same "prepare architecture, don't build the integration" precedent as `ImagingOrder`'s PACS fields).

Tax (Correction #4, approved; **implemented in Phase 4**): tax is a configurable rate attached per `service` (`tax_rule` table, with an org-wide default when no service-specific rule matches), not a flat hardcoded percentage — required groundwork for future ZATCA/regional e-invoicing compliance (spec.md §77). No `TaxRule` configured at all (the Phase 4 default state) means 0% tax, a valid self-pay-clinic configuration, never a fabricated nonzero fallback. Rounding policy: computed and rounded **per invoice line**, then summed for the invoice total (locked convention, verified live in Phase 4 testing). Jurisdiction-based rule selection (vs. today's service-based selection) is deferred until a real multi-jurisdiction deployment need names it.

## 7. Inventory Workflow

```
Purchase Request → Approval → Purchase Order → Goods Receipt → Stock Ledger Entry (in, new ProductBatch)
 → Consumption (treatment consumption via billing / manual adjustment / transfer) → Stock Ledger Entry (out, FEFO batch selection)
 → Reorder Alert (low stock / near expiry / expired)
```

**Status: implemented in Phase 5** (`src/lib/domains/inventory/*`, `src/lib/domains/procurement/*`). Stock balance is always a derived aggregate over `stock_ledger_entry`; no table stores a directly-mutable quantity — not even `ProductBatch.receivedQuantity`, which is a historical fact about what a receipt brought in, not a running balance. A materialized balance cache is an accepted future optimization (BLUEPRINT.md §"Scalability Issues"), not built until profiling in Phase 14 shows it's needed.

Automatic clinical consumption (spec.md §44, `ServiceProductConsumption` templates) is triggered from the billing engine's Charge-creation chokepoint (`src/lib/domains/billing/charges.ts`), not from CPOE order completion — Charge already carries the `serviceId` needed to look up a template and already fires for every path a service gets billed through (system-generated or POS ad-hoc), so this covers the spec requirement without reopening Phase 3's CPOE model or Phase 4's deferred automatic-procedure-charge decision. Consumption runs in the same transaction as the Charge; insufficient stock throws and the whole Charge is rolled back, not just skipped.

**Direct retail product sales consume inventory the identical way, as of the P1 remediation pass (Batch 3, §9-§11, 2026-08-27)** — closing a real gap the Phase 14 audit found (P1_FINANCIAL_INTEGRITY_FINDINGS.md's B1): a POS charge with `sourceType: "product"` previously had no `productId` field at all, so it billed the patient without ever touching a shelf. `Charge.productId`'s presence (not `sourceType`) is what `insertCharge` checks; when set, the same `consumeStock()` call in the same transaction runs, and the resulting cost feeds a `ProductSold` outbox event that posts `Dr COGS / Cr Inventory Asset` (`postProductSaleCogs`, §6) the moment the stock actually left the shelf — not deferred to whenever the charge is later invoiced. Voiding a product-sale charge (only reachable while still `status: "pending"`) reverses both sides: the stock consumption via a mirrored positive ledger entry, and the COGS via `postProductSaleVoided`, an exact reversal of what was actually posted, never a recomputation.

FEFO (spec.md §42) is a real multi-batch allocation, not a single-oldest-batch shortcut: `consumeStock()` walks every batch with remaining balance in expiry-date order (nulls last), taking from each until the requested quantity is satisfied, throwing if total availability falls short — and, as of P1 Batch 3, returns the exact per-batch cost of what it allocated (specific identification; see INVENTORY.md's "Valuation Method" for why this is the accounting valuation basis, distinct from FEFO's own physical-allocation role). Manual stock adjustments (`recordAdjustment`) with real financial impact — `damage`/`expiry`/a count-correction `adjustment` — likewise post through the central posting service (`postInventoryAdjustment`: `Dr Inventory Write-off Expense / Cr Inventory` for a loss, the mirror for a gain), valued at the specific batch's cost when one is given, the product's own `purchaseCost` as a fallback when it isn't. A manual `return`-type adjustment deliberately posts nothing — see INVENTORY.md for why.

Procurement follows Purchase Request → Approval → Purchase Order → Goods Receipt → Supplier Invoice → Payment (spec.md §46), with Approval a distinct permission from request creation (segregation of duties, same pattern as Phase 4's refund workflow). Partial receiving is supported by construction — `PurchaseOrderLine.receivedQuantity` is derived from summing `GoodsReceiptLine` rows, never stored, so multiple receipts against one PO can't drift from the truth — and `createGoodsReceipt` rejects any line that would push that derived total past the PO line's ordered quantity unless explicitly authorized (P1 §16). Goods Receipt, Supplier Invoice, and Supplier Payment all post real journal entries via the same central posting service as the revenue side: **`postGoodsReceiptCompleted`: Dr Inventory / Cr Goods Received Not Invoiced** (a GR/IR clearing account, not AP directly — P1 §15); **`postSupplierInvoiceCreated`: Dr Goods Received Not Invoiced (PO-linked) or Dr Inventory (standalone) + optional Dr Recoverable Tax / Cr Accounts Payable** — this is what actually recognizes AP, clearing whatever the goods receipt provisionally recognized; **`postSupplierPaymentRecorded`: Dr AP / Cr the paying tender's account**. See ARCHITECTURE.md's Chart of Accounts section above for the full GR/IR reasoning.

## 8. HR, Payroll & Assets Workflow

```
Employee → Schedule → Attendance → Leave → Payroll → Payslip → Payment → Accounting Journal
Asset → Maintenance / Calibration → Alert (warranty expiring / calibration due)
```

**Status: implemented in Phase 7** (`src/lib/domains/hr/*`, `src/lib/domains/payroll/*`, `src/lib/domains/assets/*`). `Employee` is the HR master; `Provider.employeeId` (a nullable, unique FK dormant since Phase 2) links it to the clinical scheduling/billing identity — two separate, both-optional concerns, wired together for real this phase via a small dedicated link action rather than folded into the full Provider edit form.

Leave approval directly affects scheduling (spec.md §51): approving a `LeaveRequest` for an employee linked to a Provider creates a `ProviderLeaveBlock` via the `EmployeeLeaveApproved` handler — the identical mechanism Phase 2's booking-conflict check already reads, so a doctor's approved leave blocks new appointments through the exact same code path a manually-entered leave block would.

**P1 Batch 6 — leave-balance entitlement + existing-appointment conflict (§25):** `approveLeave` previously approved unconditionally — `listLeaveBalances` could always compute a correct `remainingDays`, but nothing ever called it before flipping a request to `approved`. Now checked transaction-safely (`SELECT ... FOR UPDATE` locks the relevant `LeaveBalance` row so two concurrent approvals against the same entitlement can't both read the same stale used-days total — the same aggregate-lock discipline P1 Batch 4's `returnDispensingRecord` established), skipped entirely for `unpaid` leave (that type exists specifically to not draw against an allocated-days entitlement) and skipped when no `LeaveBalance` row is configured for that (employee, leaveType, year) at all (nothing configured, nothing to violate — same reasoning `getTaxRate` already applies with no `TaxRule`). An explicit `allowOverride` flag is the "authorized override" P1 §25 itself allows, gated by nothing more than the existing `leave.approve` permission (no new permission invented, matching Batch 4's over-receipt-authorization precedent). Separately, `EmployeeLeaveApproved`'s handler now also checks EXISTING appointments against the newly-approved leave window (`assertNoLeaveConflict` only ever guarded *new* bookings against an *already-approved* leave block — it can't retroactively catch an appointment that predates the approval) and creates an admin `Notification` per conflict, **never** auto-cancelling or auto-rescheduling — a human has to act on it.

Provider Commissions (spec.md §53): `CommissionRule` resolves most-specific-wins across (provider, service) → (provider, org-wide-service) → (org-wide-provider, service) → (org-wide-provider, org-wide-service), supporting fixed/percentage/tiered types against gross-invoice/net-invoice/collected-revenue bases. Two distinct trigger points, chosen for correctness rather than convenience: gross/net-invoice-basis rules accrue once at `InvoiceIssued` (the amount doesn't change with how many payments eventually settle it); collected-revenue-basis rules accrue per payment, proportional to what that specific payment actually collected (keyed to a real `Payment` row id, so redelivery-safe). Accruals never post to the ledger on their own — they're pulled into a `PayrollRunLine.commission` figure at payroll time and reach `journal_line` only as part of that combined posting.

**P1 Batch 5 — commission reversal on refund (§19):** closed P1_FINANCIAL_INTEGRITY_FINDINGS.md's B11 — a refund previously never touched `CommissionAccrual` at all, so a provider kept the full commission on revenue that was later given back, unconditionally. `reverseCommissionsForRefund` (`payroll/commissions.ts`), fired from the same `RefundCompleted` outbox event `postRefundCompleted` already handles, inserts a NEGATIVE `CommissionAccrual` row (never edits/deletes the original, spec.md §92) proportional to how much of the underlying payment was refunded. Deliberately scoped to `collected_revenue`-basis accruals only — `gross_invoice`/`net_invoice`-basis accruals are left untouched, a real "follow configured policy" decision (one of P1 §19's own three accepted outcomes), not an oversight: those two bases exist specifically to pay commission on what was billed, independent of collection risk, and a refund reduces `Invoice.paidAmount` only, never the original charge/invoice-line those bases are keyed to. The reversal row's `status` defaults to `pending` like any other accrual, so it flows through the *next* payroll run's normal pickup (`createPayrollRun`, payroll.ts) regardless of whether the original accrual was still `pending`, already `included_in_payroll`, or already `paid` — no special-cased "undo a paid commission" path was needed. See `test/integration/commission-refund-integrity.test.ts`.

Payroll (spec.md §52): Draft → Review → Approved → Paid. Creating a run snapshots each employee's `basicSalary` plus their pending commission accruals (immediately marking those `included_in_payroll` so a second run can't double-count them); `netSalary` is fixed once computed, the same "historical fact once finalized" precedent as `Invoice.totalAmount`. Approved posts `Dr Salary Expense / Cr Payroll Payable` (spec.md §55's own named payroll example) via two new `PostingIntent`s (`salary_expense`, `payroll_payable`); Paid posts `Dr Payroll Payable / Cr [the run's tender account]` — both through the same central posting service as every Phase 6 posting, using `netSalary` on both sides of both postings (deductions are netted into the expense figure, not modeled as a separate payable — see PROJECT_STATUS.md's Phase 7 Known Issues for what this trades away).

**P1 Batch 5 — payroll posting idempotency, verified (§18):** `postJournal`'s existing-journal check keyed on `(referenceType, referenceId)` — `payroll_run` for `postPayrollApproved`, the deliberately distinct `payroll_run_paid` for `postPayrollPaid` (§15, P0-02) — was re-verified with real DB replay tests (`test/integration/payroll-lifecycle-integrity.test.ts`): calling either posting function twice for the same run posts exactly one journal, and Approved/Paid always produce two genuinely separate journals, never one silently skipped as a "duplicate" of the other. **Not fixed in this batch, and still open**: P1_FINANCIAL_INTEGRITY_FINDINGS.md's B10 — `approvePayrollRun`/`markPayrollPaid` (payroll.ts) still call their posting functions *outside* any transaction with the state change and outside the outbox, unlike every other financial-posting trigger in this codebase. If `postPayrollApproved` throws (most plausibly a missing `salary_expense`/`payroll_payable` account mapping), the run is already committed to `"approved"` with no journal and no outbox-tracked retry path — the service layer's own "already approved" guard then blocks a normal re-approval, leaving a manual journal entry as the only recovery. Batch 5's instructions asked specifically to confirm the existing referenceType-keyed idempotency holds under replay, not to rewire payroll onto the outbox pattern (a larger, distinct fix B10 would require) — flagged here for a future batch rather than addressed unprompted.

Assets (spec.md §47/§48): `Asset` tracks the full named field set including all seven statuses; `MaintenanceRecord`/`CalibrationRecord` are its history. No accounting posting on asset purchase — the physical purchase already flows through Expense or the procurement chain if bought that way, and spec.md §47 doesn't name a dedicated posting the way Payroll does. Warranty and calibration-due alerts are computed live against a 30-day horizon, never stored flags — the same discipline as Phase 5's stock alerts.

## 9. Laboratory (LIS) Workflow

```
Doctor Order (ClinicalOrder + LabOrderDetail, free-text intent, Phase 3)
 → Assign Tests (structured LabOrderTest lines from the LabTest/LabPanel catalog + Charge generated, Phase 8)
 → Specimen Collection → Result Entry (abnormalFlag computed server-side)
 → Verification → Final Result → Patient EMR + LabResultFinalized
```

**Status: implemented in Phase 8** (`src/lib/domains/laboratory/*`). A deliberate two-stage model: the doctor's Phase 3 CPOE lab order captures clinical *intent* only (free-text `testName`) and is left completely untouched by this phase; lab staff then "assign" catalog `LabTest`/`LabPanel` entries against that order, which is the point structured, billable `LabOrderTest` rows and their `Charge`s (`sourceType: "lab"`, defined in Phase 4, unused until now) get created — one `Charge` per test, one per panel (covering all its members, not one per member). A `LabPanel` expands into one `LabOrderTest` per member test at assignment time, each independently resulted and verified, since a panel like CBC produces several distinct results with different reference ranges, not one combined value.

`Specimen` is its own table (one specimen commonly services several `LabOrderTest` lines from one physical draw), with its own pending → collected → received → rejected lifecycle. `LabOrderTest.unit`/reference range are snapshotted from the catalog at **result-entry time**, not order-assignment time, since that's the actual clinical-interpretation moment — a later catalog edit never rewrites an already-entered result's context, the same discipline as `InvoiceLine`'s snapshot fields. `abnormalFlag` is always computed server-side from the entered value against the snapshotted range, never client-submitted.

`lab_result.enter` vs `lab_result.verify` are distinct permissions (segregation of duties, reserved since Phase 1's permission catalog, actually exercised for the first time this phase). Verifying the last outstanding `LabOrderTest` on an order rolls `ClinicalOrder.status` to `completed` and fires `LabResultFinalized` — reserved in this file's event table since Phase 2, wired for real only now (§15).

**P1 Batch 6 — centralized state-transition validation (§20):** a real, concrete instance of the exact bug P1 §20 warns about by name — `updateOrderStatus` (clinical/orders.ts) accepted any of `acknowledged`/`in_progress`/`completed`/`cancelled` as a target with **zero check against the order's current status**, meaning a caller could jump `ordered` straight to `completed` (P1's own "ORDERED -> FINALIZED" example) or move a `completed`/`cancelled` order backward. `assignTests`/`assignImagingService` had the identical gap in miniature (flipping `ClinicalOrder.status` to `in_progress` with no precondition check at all), and `enterNumericResult`/`enterTextResult` (laboratory/results.ts) only ever blocked re-entry after `verified` — a result could be entered directly against a line that was never actually `collected`. Fixed with one new shared primitive, `assertValidTransition` (`src/lib/platform/state-machine.ts`) — a generalization of `appointments/service.ts`'s own `transition()` helper (which already proved this exact pattern out for `Appointment`) — checked through by two new per-model transition maps, `CLINICAL_ORDER_TRANSITIONS` (clinical/orders.ts) and `LAB_ORDER_TEST_TRANSITIONS` (laboratory/results.ts), covering P1's own literal ladder (ORDERED → ACKNOWLEDGED → SAMPLE_COLLECTED → PROCESSING → RESULT_ENTERED → VERIFIED). `cancelOrder` is the new dedicated Clinical-Order cancellation path (§24) — always through the same map, always capturing a reason.

**P1 Batch 6 — critical abnormal flags and amendment (§21/§22):** `AbnormalFlag`'s `critical_low`/`critical_high` enum values (and the UI's own `FLAG_VARIANT` badge colors for them) existed since early in this build but were never actually computed — `computeAbnormalFlag` only ever returned `low`/`high`/`normal`, with a doc comment explicitly noting "no critical-threshold auto-detection." Closed by adding `LabTest.criticalLow`/`criticalHigh` (nullable — critical is determined only where configured, never fabricated) and rewriting `computeAbnormalFlag` to check them first. A verified critical result now fires `CriticalLabResultVerified`, notifying the ordering provider (falling back to any `lab_result.verify` holder only if the provider has no linked login) — restricted by construction, since every `Notification` row is addressed to one specific recipient, never broadcast. §21's "amended finalized results keep history" gap is closed with the exact `isCurrent`/`amendsId` chain shape `ClinicalNote` (Phase 3) already established for the identical problem — reused via `amendLabResult`, not reinvented; every read path that shows verified results (`listPatientLabResults`, the lab report print view, the operational order detail page) now also filters `isCurrent: true` so an amended result never shows twice.

## 10. Pharmacy (PIS) Workflow

```
Doctor Order (Prescription + PrescriptionItem, free-text intent, Phase 3)
 → Create DispensingRecord (structured, catalog-referenced, quantity, Phase 9)
 → Verify → Dispense (Inventory Reduction → Billing → Patient Medication History, one transaction)
 → [optional] Return (correcting record, stock added back — never edits the original dispensing)
```

**Status: implemented in Phase 9** (`src/lib/domains/pharmacy/*`). The identical two-stage model Phase 8 built for lab orders, deliberately reused rather than reinvented: the doctor's Phase 3 `Prescription`/`PrescriptionItem` (free-text `medicationName`) captures clinical intent only and is left completely untouched; pharmacy staff then create one or more structured `DispensingRecord` rows against a catalog `Medication` per prescription item, supporting partial fills across visits (remaining-to-dispense always derived live by summing `quantityDispensed` across non-cancelled records, never a stored counter).

`Medication` is a 1:1 companion to `Product` (`productId` UNIQUE FK), not a parallel item master — stock, batches, expiry, and cost are all inherited from the existing Phase 5 inventory machinery wholesale, the same "extend, don't duplicate" precedent `CommissionRule` set for `Product` in Phase 7.

`prescription.verify` vs `prescription.dispense` are distinct permissions (segregation of duties, the same enter/verify pattern as `lab_result.enter`/`verify`). Dispensing itself (`dispenseRecord()`) does inventory reduction, billing, and patient medication history update **all in one transaction**, matching spec.md §29's named ordering exactly: `consumeStock()` (Phase 5, extended with an optional `transactionType: "dispensing"` parameter rather than a second consumption function) walks FEFO batches; `generateSystemCharge()` bills through the same chokepoint every other automatic charge uses (`sourceType: "pharmacy"`, defined in Phase 4, unused until now); `PatientMedicationHistory` is updated to `current`. A stock shortfall rolls back the whole transaction, not just the stock step — the same discipline as Phase 5's over-consumption guard.

Returns (`DispensingReturn`) are correcting records, never edits to the original `DispensingRecord` — adds stock back via a `return` ledger entry, rejects returning more than net-outstanding (dispensed minus prior returns), and never touches the original `Charge`.

The pharmacy-disable capability spec.md §29 explicitly requires ("architecture must allow pharmacy to be disabled for clinics that do not operate one") is implemented by finally wiring up the generic `Setting` table (`src/lib/platform/settings.ts`) — reserved in the schema since Phase 1, never consumed by any domain until now — rather than a new ad-hoc flag mechanism. Every dispensing action checks `isPharmacyEnabled()`; the medication catalog and queue remain viewable regardless.

## 15. Domain Event / Outbox Architecture

`outbox_event` row written in the same transaction as the state change (`writeOutboxEvent`, `src/lib/platform/outbox.ts`). The primary dispatch path is **not** a timer-driven background poller — it's `dispatchPendingOutboxEvents(organizationId)` called immediately after the writing transaction commits, from the same service function (see `patients/service.ts` and `appointments/service.ts`), scoped to that write's own organization for low latency. A true periodic sweep now also exists as a *second*, complementary path (P1 §4 — see below) precisely because the inline path's per-organization scoping means nothing else re-checks a different organization's due retry, or recovers a crashed process's stuck event, unless something calls it. Event list is fixed to what spec.md §73/§93 names explicitly — no speculative additions.

**Reliability, reworked in the P0 remediation pass (P0-02, 2026-08-27)**: the original design's `failed` status was a dead end — the dispatcher only ever queried `pending`, so a failed event never got a second chance, meaning (for example) a successfully-issued invoice could end up with no accounting journal and no automatic recovery. Replaced with an explicit state machine: `pending → processing → completed`, or `pending → processing → failed` (with `attempts`/`lastAttemptAt`/`nextRetryAt`/`lastError` tracked, and increasing retry delays — 1min / 5min / 20min) `→ ... → dead_letter` after 3 attempts, which also creates an internal `Notification` for every Super Admin / Organization Administrator so a persistent failure is visible rather than silent. A `/admin/system-events` UI (`system_events.view`/`system_events.retry`) shows every event's status/attempts/error with a manual-retry action. Because retries mean a handler can now genuinely run twice, idempotency was centralized in `postJournal` (§6) — the one function every accounting posting funnels through — via an existing-record check keyed on `referenceType`+`referenceId`, rather than duplicating a check in each of the eight named posting functions. See DATABASE.md's "P0 Remediation Schema Changes" for the schema change and P0_REMEDIATION_REPORT.md's P0-02 section for full detail, including a real latent bug this centralization caught (`postPayrollApproved`/`postPayrollPaid` sharing one `referenceType`, which would have made the second posting silently no-op).

**Crash recovery and periodic sweep, added in the P1 remediation pass (P1 §3/§4, 2026-08-27)**: P0-02's state machine still had one real gap — an event stuck in `processing` because the process that claimed it died mid-handler (a killed serverless invocation, a deploy that terminated an in-flight request) had no way back to `pending`/`failed`; nothing ever re-queried `processing` rows at all. Fixed with a configurable timeout (`OUTBOX_PROCESSING_TIMEOUT_MS`, default 5 minutes — see the constant's own doc comment in `outbox.ts` for why that's long enough to never misclassify genuinely in-flight work) and `recoverStaleProcessingEvents()`: an event stuck past the timeout is returned to `failed` with `nextRetryAt` set to now (or straight to `dead_letter` if it had already exhausted its retries — a stuck attempt is still an attempt), using the same atomic conditional-`updateMany` claim pattern as the primary dispatch path, so two concurrent recovery sweeps can't both reclaim the same stuck event any more than two dispatchers can both process the same pending one (P1 §5, proven in `test/integration/outbox-concurrency.test.ts`). `processPendingOutboxEvents()` is the new organization-agnostic entry point that runs recovery, then dispatches every organization's due pending/failed events in one call — the periodic-sweep counterpart to the per-organization inline path above, callable from a cron job (`src/app/api/cron/outbox-sweep/route.ts`, scheduled via `vercel.json`), any other scheduler, or an admin's "Sweep now" button on `/admin/system-events`. No queue/broker was introduced for this — a plain function callable from an HTTP endpoint on a schedule is all a bounded, idempotent batch sweep needs, the same "no unnecessary distributed infrastructure" discipline the paragraph above already established. See DEPLOYMENT.md's "Outbox Sweep Scheduling" for the production scheduling requirement and `test/integration/outbox-crash-recovery.test.ts` for the recovery-correctness tests (including that an event still within the timeout window is deliberately left untouched, not assumed crashed).

## 16. Permission Enforcement Chokepoint

Single function `can(session, permission, { branchId?, resourceOwnerId? })` in `/lib/platform/permissions-core.ts`. Called at three layers: middleware (route-level default-deny), service layer (business-rule-level), and query-projection layer (field-level — reception's `patient.view` excludes clinical-note fields per BLUEPRINT.md's Security Risks correction on field-level scoping). No layer trusts the layer above it.

**Branch scope — a second, orthogonal chokepoint, centralized in the P0 remediation pass** (P0-01, 2026-08-27): `can()` answers *what* a session may do; `src/lib/platform/branch-scope.ts` answers *where* — `getAuthorizedBranchScope(session)` resolves the session's organization/authorized-branches/org-wide-bypass once, `narrowBranchFilter()`/`assertBranchAccess()` are what every `list*`/`get*` domain function now calls to enforce it, rather than each function inventing its own (often-missing) branch check. This existed only inconsistently before the P0 pass — the Phase 14 audit found several read paths that trusted a client-supplied `branchId` outright. See SECURITY.md §2 and P0_REMEDIATION_REPORT.md's P0-01 section for full detail.

## 17. Analytics Workflow

```
Dashboards: session permissions -> visibleDashboardSections() -> {Management,Reception,Doctor,Finance} sections (spec.md §8, /dashboard)
Reports: session permissions -> canViewReportCategory() -> {Practice,Clinical,Financial,Revenue Cycle,Inventory,HR,Assets} tabs (spec.md §65, /reports)
KPIs: getKpiTrends() -> 6-month bucketed trend -> CSS bar charts (spec.md §65, /analytics)
Exports: reports.export permission -> GET /api/reports/export?category=...&from=...&to=... -> CSV
```

**Status: implemented in Phase 13** (`src/lib/domains/analytics/*`, `src/app/(dashboard)/dashboard`, `src/app/(dashboard)/reports`, `src/app/(dashboard)/analytics`, `src/app/api/reports/export`).

**No new tables, no new permissions** — every dashboard tile, report row, and KPI point is a live query against a table another domain already owns (Appointment, Invoice, Payment, Encounter, Diagnosis, ClinicalOrder, Claim, StockLedgerEntry, AttendanceRecord, LeaveRequest, PayrollRun, CommissionAccrual, Asset, MaintenanceRecord, CalibrationRecord — see §2's domain map for who owns what), gated by the existing view permission that domain already checks (`appointment.view`, `encounter.view`, `accounting.view`, `invoice.view`/`claim.create`, `inventory.view`, `payroll.view`) rather than a parallel `report.view`/`dashboard.view` permission invented to match. The Management Dashboard section is the one exception worth naming: it reuses `reports.export` (already scoped to exactly the management-tier roles) as its visibility gate, not because it exports anything, but because that permission already encodes "this role sees cross-cutting operational summaries."

**Dashboards are sections on one page, not one page per role** — `visibleDashboardSections()` checks the four section-gating permissions independently and a user sees every section they qualify for (a Clinic Manager, holding both `reports.export` and `accounting.view`, sees Management *and* Finance). The Doctor section is gated differently from the other three — not a permission at all, but whether the signed-in `User` has a linked `Provider` row (`Provider.userId`, reserved since Phase 2 for exactly this purpose per its own doc comment) — since "my schedule, my patients" is an identity question, not a permission question.

**Reports reuse rather than reimplement wherever a function already exists**: the Financial category's P&L/Balance Sheet/Cash Flow are `accounting/reports.ts`'s own Phase 6 functions, called directly, not reimplemented against `journal_line` a second time (API.md §1's "no business rule is ever implemented twice for the same operation"). Where no aggregate existed yet (Practice's provider/room utilization, Clinical's diagnosis trends, HR's attendance/leave/commission rollups, Assets' register/maintenance/calibration summaries), Phase 13 wrote new, real aggregate queries directly in `analytics/reports/*.ts` — reports are inherently a new aggregation layer over existing data, not something every domain was expected to pre-build for itself.

**CSV export is this codebase's first real `/api/*` Route Handler** — every prior phase's mutations went through Server Actions; a file download needs a browser-navigable URL with real `Content-Disposition`/`Content-Type` headers, which a Server Action can't produce. `src/app/api/reports/export/route.ts` sits behind the same staff `proxy.ts` session check as every other non-public route (no new route class was needed) and independently re-checks both `reports.export` and the specific category's view permission — the same "service layer never trusts the layer above it" discipline as everywhere else (§16).

**No charting library** — `/analytics`'s six trend charts are plain CSS bars (height as a percentage of the period's max value), not a Recharts/Chart.js dependency. Consistent with this build's standing "no unnecessary complexity" discipline (§15's "no unnecessary distributed infrastructure," §13's "no fake scheduler") — six simple monthly bars don't need a charting library, though a future need for richer visualization (multi-series, zoom, tooltips) would be a legitimate reason to add one.

**Deliberately not built this phase**: Global Search (spec.md §66) and the master-data bulk Import/Export workflow (spec.md §83) — neither is named in spec.md's literal numbered Phase 13 "Implement" list (Dashboards/Reports/KPIs/Exports), the same "follow the literal phase directive" discipline Phase 12 applied to Lead CRM (§13).
