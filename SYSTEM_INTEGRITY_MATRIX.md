# System Integrity Matrix

Per P1.md §41 — an ongoing architecture reference, not a one-time snapshot. Whenever a new workflow is added to this codebase, or an existing one's transaction/idempotency/accounting/inventory shape changes, update its row here. Every claim below is backed by a currently-passing test cited in the **Tests** column — see [P1_REMEDIATION_REPORT.md](P1_REMEDIATION_REPORT.md) for the full remediation history behind each one, and [TRANSACTION_BOUNDARIES.md](TRANSACTION_BOUNDARIES.md) for the deeper design narrative on the transaction boundaries specifically.

**Column definitions:**
- **Source Transaction** — the domain function that triggers this workflow.
- **Dependent Records** — every row/table this one workflow writes, in the same business action.
- **Transaction Protected?** — do all the dependent writes commit or roll back together?
- **Idempotent?** — does a double-click or network retry produce the same result as a single submission, not a duplicate?
- **Accounting Impact?** — the journal entry this workflow posts, if any, and which posting function.
- **Inventory Impact?** — does this workflow move real stock?
- **Audit Event?** — is the action recorded in `audit_log` (mutation audit) and/or as an outbox domain event?
- **Tests?** — the test file(s) proving the row's other claims.

## Reading this matrix

- **Every "Yes" is backed by a real DB integration test, not a code-review assertion.** Where a claim is qualified (e.g., Procedure Completion's Accounting/Inventory Impact) the qualification is the actual, verified behavior — not a placeholder for "not yet implemented."
- **Every "No" is a real, currently-open finding**, not a template gap. This pass found and closed the equivalent gap for every workflow that had one *and was explicitly named in P1.md's own §33 idempotency list* (Invoice Issued, Payment Received, Refund Issued, Goods Receipt, Dispensing, Procedure Completion, Payroll Approval, Payroll Payment, Package Usage — all nine, all `Yes`). Product Sale and Supplier Invoice were not on that list; their idempotency gaps were discovered while building this matrix and are reported here rather than silently left undiscovered or fixed outside this batch's authorized "synthesis and sign-off only" scope.
- **Transaction Protected? being "Yes" everywhere** reflects real work across Batches 2, 3, 4, 7, and 8 — it was not always true; see [TRANSACTION_BOUNDARIES.md](TRANSACTION_BOUNDARIES.md) for which workflows needed a fix and which were already correct.
