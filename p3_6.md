# 1. PURPOSE

P3.6 is:

# PHARMACY / PRESCRIPTION / DISPENSING WORKFLOW

This is NOT another whole-system audit.

The objective is:

> Make a doctor's prescription flow coherently from the Encounter into Pharmacy, through pharmacist review and dispensing, with safe inventory movement, clear dispensing history, and appropriate return visibility to the Doctor and Patient 360.

Conceptual workflow:

Doctor Encounter
→ Prescription
→ Pharmacy Queue
→ Pharmacist Reviews
→ Medication Availability
→ Dispense
→ Inventory Consumption
→ Dispensing Record
→ Prescription Status
→ Doctor / Patient 360 visibility

Billing integration should use the existing billing architecture where it already exists.

Do NOT build another billing system.

---

# 2. IMPORTANT ARCHITECTURAL PRINCIPLE

The existing system deliberately keeps:

Prescription

separate from:

ClinicalOrder.

Preserve that.

Do NOT convert medication prescriptions into ClinicalOrder.

Prescription represents the doctor's medication instruction.

Dispensing represents Pharmacy fulfillment.

Inventory movement represents physical stock movement.

Billing represents the financial transaction.

These are related but distinct events.

# 18. INVENTORY CONSUMPTION

This is critical.

Dispensing should create stock movement through the existing inventory architecture.

Prescription
→ Dispense
→ Batch
→ Stock Ledger

---

# 19. INVENTORY ATOMICITY

A dispense operation involving stock must be atomic.

Avoid:

1. mark prescription dispensed
2. then reduce stock
3. stock reduction fails
4. prescription remains dispensed

or the reverse.

Use a database transaction through existing domain patterns.

If current dispensing is not atomic, fix it.

---

# 20. CONCURRENT DISPENSING

Test realistic race:

Two pharmacists open the same pending prescription.

Both click Dispense.

The system must not:

* double dispense
* double consume inventory
* double charge
* overwrite dispenser identity

Use server-side state/conditional-update guards.

Do not rely solely on disabled buttons.

A database constraint/status claim/idempotency mechanism should protect the operation.

---

# 21. CONCURRENT STOCK
