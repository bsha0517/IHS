P3 is:

# OPERATIONAL UX & WORKFLOW POLISH

Do NOT redesign the architecture.

Do NOT introduce microservices.

Do NOT start regulatory integrations yet.

P3 must concentrate on:

* workflow continuity
* usability
* navigation
* operational efficiency

* useful empty states

* reducing unnecessary clicks
* making existing capabilities reachable
* eliminating awkward workflow dead ends

Do not sacrifice P0/P1/P2 integrity protections to improve UX.

# 2. IMPORTANT WORKING METHOD

Do NOT perform a giant whole-system audit first.

Work through P3 in bounded workflow batches.

For each batch:

1. Inspect only relevant pages/components/domain functions.
2. Understand the current workflow.
3. Identify concrete usability/workflow gaps.
4. Implement the improvements.
5. Add/update targeted tests.
6. Run relevant tests.
7. Run the full integration suite.
8. Run typecheck/lint/build.
9. Write a concise batch report.
10. STOP before starting the next batch unless instructed to continue.

Do not repeatedly ask for approval for ordinary implementation decisions within the authorized batch.

If you find unrelated issues:

Add them to `BACKLOG.md`.

Do NOT fix them unless they create:

* patient-data corruption
* clinical-record corruption
* financial corruption
* security/privacy breach
* destructive database behavior

# 7. APPOINTMENT STATUS ACTIONS

The appointment lifecycle already exists:

scheduled
→ confirmed
→ arrived
→ checked_in
→ waiting
→ in_consultation
→ completed

with:

* cancelled
* rescheduled
* no_show

Do NOT change this lifecycle casually.

Instead ensure the UI makes valid next actions obvious.

Example:

Scheduled appointment:

* Confirm
* Mark Arrived
* Reschedule
* Cancel

Confirmed:

* Mark Arrived
* Reschedule
* Cancel

Arrived:

* Check In

Checked In:

* Send to Waiting

Waiting:

* normally handed to clinical workflow

Do not show impossible transitions.

Server-side transition validation remains authoritative.

UI controls should reflect those same rules.

# 9. WALK-IN PATIENT WORKFLOW

A real clinic needs a clean walk-in workflow.

Inspect whether the current system supports this naturally.

Desired experience:

Search patient

→ Existing patient found

OR

→ Register new patient

→ Select provider/service

→ Find available slot / immediate availability

→ Create appointment

→ Mark arrived/check-in

→ Place patient into queue

Do not create a separate incompatible WalkIn model if Appointment already represents this correctly.

Use the existing Appointment architecture.

If useful, distinguish source/type through existing fields or a small safe extension.

Do not bypass double-booking protections.

# 10. PATIENT SEARCH

Reception patient search should be fast and forgiving.

Review support for:

* MRN
* patient name
* phone/mobile
* national ID / identity field where currently supported

Do not expose cross-organization patients.

# 11. DUPLICATE PATIENT WARNING

The existing system warns rather than automatically blocking duplicate patient registration.

Preserve that design.

Improve the operational experience if needed:

When potential duplicates are detected:

Show likely matches clearly.

Allow receptionist to:

* open existing patient
* continue registration when genuinely different

If overriding the duplicate warning:

preserve the existing audited override reason.

Do not silently merge patients.

A proper patient merge workflow belongs to a later phase.

* notes/reason if supported

---

# 14. RESCHEDULING

The current architecture correctly creates a new appointment linked through:

`rescheduledFromId`

and preserves history.

Do NOT replace this with overwriting the original appointment.

Improve the UX around this model.

Receptionist should clearly see:

Original appointment

→ Rescheduled

→ New appointment

The patient should not appear accidentally twice in the active queue.

Appointment history should make the relationship understandable.

---

# 15. CANCELLATION

Cancellation should:

* require an appropriate reason where the current domain supports it
* preserve history
* clearly update the UI
* remove the appointment from active operational queues where appropriate

Do not delete appointments.

---

# 16. NO-SHOW

Make no-show handling practical.

Reception should be able to identify appointments whose scheduled time has passed and mark them as no-show.

Do NOT automatically mark appointments no-show merely because time passed unless such automation already exists and is safe.

A receptionist-confirmed action is acceptable for V1.

Derive duration from persisted appointment/status-history data.

Do not store continuously updating elapsed values.
