# 1. PURPOSE

P4.2 is:

# DATABASE RELIABILITY / BACKUP / RESTORE / DISASTER RECOVERY

The objective is:

> Prove that clinic data can be safely backed up, restored, verified, and recovered after realistic database failures or deployment accidents.

This phase is NOT complete merely because Supabase/PostgreSQL offers backups.

The central principle is:

> A backup that has never been restored is not yet a proven backup.

P4.2 must therefore include an ACTUAL controlled backup-and-restore drill.

# 8. INDEPENDENT BACKUP PRINCIPLE

A production database and every backup copy should not share one failure domain.

If production is on Supabase:

an independent logical backup should ideally be stored outside the same Supabase project.

Potential future destinations:

* S3
* R2
* Azure Blob
* another secure backup target

Do not wire a cloud storage provider unless needed for this phase.

A local encrypted drill backup is sufficient for the actual test.

# 9. LOGICAL BACKUP SCRIPT

If none exists, implement a safe backup script.

Preferred underlying tool:

`pg_dump`

Use the privileged/direct PostgreSQL connection where required.

Do NOT use the transaction pooler for backup operations.

Potential output:

custom format:

`.dump`

because it supports flexible `pg_restore`.

Requirements:

* timestamped filename
* clear failure behavior
* no credentials in filename
* no credentials printed
* backup directory configurable
* production-safe shell behavior
* non-zero exit on failure
